## Story

**As a** usuário,
**I want** reordenar meus links arrastando,
**so that** a ordem visual da minha página pública reflita minhas prioridades.

## Acceptance Criteria

1. Cada link tem handle de drag (icon ⋮⋮ à esquerda) ativo em mouse + touch.
2. Drop persiste nova ordem otimisticamente (UI atualiza imediato); rollback com toast se Server Action falhar.
3. Reorder dispara batch update transacional de positions afetadas.
4. Acessibilidade: alternativa via teclado (botões ↑/↓ no menu de cada link).
5. Testes de integração cobrem reorder de 5 links.

### Reorder atômico — POR QUE uma função Postgres (RPC) é obrigatória

`schema-design.md §7 Q1 RESOLVED` (linhas 899-926) fechou a estratégia: `UNIQUE (page_id, position) DEFERRABLE INITIALLY DEFERRED` + leave gaps on delete. O reorder atômico canônico é:

```sql
BEGIN;
  UPDATE links SET position = 1 WHERE id = 'id5' AND page_id = 'X';
  UPDATE links SET position = 2 WHERE id = 'id1' AND page_id = 'X';
  ...
COMMIT;  -- uniqueness (DEFERRED) avaliado SÓ AQUI → swap sem coluna temporária
```

**O ponto crítico:** isso só funciona dentro de **UMA transação**. O `supabase-js` (PostgREST) **não** expõe transações multi-statement no cliente — cada `.update()` é uma requisição/transação **isolada**, e `DEFERRABLE INITIALLY DEFERRED` re-avalia a constraint no COMMIT de **cada** transação. Logo, N `.update()` sequenciais **falhariam** em qualquer swap (ex.: setar `id1.position=1` enquanto `id5` ainda tem `1` → violação `23505` no commit daquele statement). A forma canônica Supabase de rodar múltiplos statements em 1 transação é uma **função Postgres chamada via `supabase.rpc(...)`** — 1 chamada RPC = 1 transação = constraint avaliada no fim da função. **Não é invenção:** é a única materialização correta da decisão arquitetural Q1 já fechada. [Source: schema-design.md §900-926; §336 ("Multi-row em transação; usa constraint DEFERRABLE"); `0004_links.sql` tail; arch §755 ("TX batch update positions")]

A função usa `unnest(p_ordered_ids) WITH ORDINALITY` para mapear cada id → seu índice (1-based) numa **única** instrução `UPDATE … FROM`, scoped por `page_id = (SELECT id FROM pages WHERE profile_id = auth.uid())`. `SECURITY INVOKER` preserva `auth.uid()` e as RLS policies → ids de outro usuário simplesmente não casam o `WHERE` (defense-in-depth sobre a própria RLS `links_update_own`).

**As a** desenvolvedor,

### DDL canônico de `pages` (verbatim — `schema-design.md §4 #pages` linhas 468-482)

```sql
CREATE TYPE theme_preset AS ENUM ('light', 'dark', 'brand');  -- §3 linha 354

CREATE TABLE pages (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  profile_id   uuid NOT NULL UNIQUE REFERENCES profiles(id) ON DELETE CASCADE,
  theme        theme_preset NOT NULL DEFAULT 'light',
  is_published boolean NOT NULL DEFAULT true,
  created_at   timestamptz NOT NULL DEFAULT now(),
  updated_at   timestamptz NOT NULL DEFAULT now()
);

CREATE TRIGGER trg_pages_set_updated_at
  BEFORE UPDATE ON pages
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();

COMMENT ON TABLE pages IS 'Página pública /@username (1:1 com profile no MVP, FR5, FR12).';
```

- `profile_id ... UNIQUE` satisfaz **AC4** (1 page/profile MVP) e cria índice automático → **sem índice extra** (`schema-design.md §4 #pages` linha 484). Phase 2 (multi-page) removerá a UNIQUE via expand-contract (`schema-design.md §10` linha 1138) — fora de escopo.
- `id` usa `gen_random_uuid()` (≠ `profiles.id` que é o auth.users.id) — `pages.id` é independente (segurança em URLs futuras `/api/pages/{id}`, `schema-design.md §7` linha 818).

### Contrato do trigger estendido `on_auth_user_created()` (AC2)

Corpo **atual** (0002:135-153) insere só em `profiles`. **Estender** via `CREATE OR REPLACE FUNCTION on_auth_user_created()` mantendo `RETURNS trigger LANGUAGE plpgsql SECURITY DEFINER SET search_path = public, pg_catalog`, o `DECLARE v_username citext := lower(coalesce(NEW.raw_user_meta_data->>'username',''));`, o guard `IF v_username = '' OR length(v_username) < 3 THEN RAISE EXCEPTION ... USING HINT = ...`, o `INSERT INTO profiles (id, username) VALUES (NEW.id, v_username);` — e **adicionar** logo após:

```sql
  INSERT INTO pages (profile_id) VALUES (NEW.id);
```

`RETURN NEW;` no fim. Atualizar `COMMENT ON FUNCTION on_auth_user_created()` para algo como _'Bootstrap profile + page (1:1) ao criar auth.users (Story 2.2). SECURITY DEFINER permite INSERT bypass RLS.'_. **Não** dropar a função; **não** precisa re-emitir o `CREATE TRIGGER auth_user_created` (substituição in-place). `SECURITY DEFINER` permite o INSERT em `pages` bypassar a ausência de policy INSERT (mesma mecânica que já permite o INSERT em `profiles`).

### Estratégia RLS de `pages` (AC3) — resumo de `schema-design.md §8` linha 940 + §9 992-994

| Operação         | Policy                | Predicado                                                | Fonte                             |
| ---------------- | --------------------- | -------------------------------------------------------- | --------------------------------- |
| SELECT (público) | `pages_select_public` | `is_published = true`                                    | §8 L940 (`is_published OR owner`) |
| SELECT (owner)   | `pages_select_own`    | `profile_id = auth.uid()`                                | §8 L940                           |
| UPDATE (owner)   | `pages_update_own`    | `USING + WITH CHECK profile_id = auth.uid()`             | §8 L940                           |
| INSERT           | — (nenhuma)           | só via trigger SECURITY DEFINER                          | §8 L940 = "trigger only"          |
| DELETE           | — (nenhuma)           | cascade via `profiles.id`→`auth.users` ON DELETE CASCADE | §8 L940 = "cascade"               |

- `auth.uid()` é STABLE no Supabase (Postgres pode cachear por linha — `schema-design.md §9` linha 994). UNIQUE em `profile_id` já indexa a coluna de filtro das policies (`schema-design.md §9` linha 993).
- Naming `{tabela}_{op}_{escopo}` espelha 0002 (`profiles_select_public`/`profiles_update_own`). `DROP POLICY IF EXISTS` antes de cada `CREATE POLICY` (idempotência, padrão 0002:101-115).

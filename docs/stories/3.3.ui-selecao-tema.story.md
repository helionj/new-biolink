## Story

**As a** usuário,
**I want** um seletor de tema com preview em tempo real,
**so that** eu veja como minha página fica antes de salvar.

## Acceptance Criteria

1. Página `/dashboard/theme` com 3 cards (preview thumbnail + nome do tema).
2. Card selecionado destacado; clique salva via Server Action.
3. Preview mini da página pública renderizada inline com o tema escolhido (iframe ou Server Component isolado).
4. Toast de confirmação após save; revalidate `/@<username>` cache.

  - [x] 5.1 Criar `components/theme/ThemeSelector.tsx` (arquivo novo). Client Component — interatividade exige `'use client'` (Coding Standards arch L2390). Estrutura completa (~80 LOC):

    ```tsx
    'use client';

    import { Loader2 } from 'lucide-react';
    import { useState, useTransition } from 'react';

    import { ThemePreview } from '@/components/theme/ThemePreview';
    import { cn } from '@/lib/utils';
    import { toast } from '@/lib/toast';
    import type { Theme } from '@/lib/theme';
    import { THEMES } from '@/lib/theme';
    import { updateTheme } from '@/server/page/actions';

    type PreviewData = {
      profile: {
        username: string;
        display_name: string | null;
        bio: string | null;
        avatar_url: string | null;
      };
      links: Array<{
        id: string;
        title: string;
        url: string;
        icon: string | null;
        position: number;
      }>;
    };

    const LABELS: Record<Theme, string> = {
      light: 'Light',
      dark: 'Dark',
      brand: 'Brand',
    };

    export function ThemeSelector({
      currentTheme,
      previewData,
    }: {
      currentTheme: Theme;
      previewData: PreviewData;
    }) {
      // Estado otimista local — UI atualiza imediato; rollback em erro.
      // (Precedente: `components/links/LinkList.tsx:48-62` para o mesmo padrão
      // optimistic + rollback + toast.)
      const [selected, setSelected] = useState<Theme>(currentTheme);
      const [pending, setPending] = useState<Theme | null>(null);
      const [, startTransition] = useTransition();

      function handleSelect(next: Theme) {
        if (next === selected || pending) return;
        const previous = selected;
        setSelected(next);
        setPending(next);
        startTransition(async () => {
          const res = await updateTheme({ theme: next });
          setPending(null);
          if (!res.ok) {
            setSelected(previous);
            toast.error(res.error);
            return;
          }
          toast.success('Tema atualizado');
        });
      }

      return (
        <div
          role="radiogroup"
          aria-label="Tema da página"
          className="grid grid-cols-1 gap-4 sm:grid-cols-3"
        >
          {THEMES.map((theme) => {
            const isSelected = theme === selected;
            const isPending = pending === theme;
            return (
              <button
                key={theme}
                type="button"
                role="radio"
                aria-checked={isSelected}
                disabled={pending !== null}
                onClick={() => handleSelect(theme)}
                className={cn(
                  'group flex flex-col gap-3 rounded-lg border-2 p-3 text-left transition focus:outline-none focus-visible:ring-2 focus-visible:ring-ring',
                  isSelected
                    ? 'border-primary ring-2 ring-primary/30'
                    : 'border-border hover:border-muted-foreground',
                  pending !== null && !isPending && 'opacity-60',
                )}
              >
                <div className="aspect-[3/4] overflow-hidden rounded-md">
                  <ThemePreview theme={theme} data={previewData} />
                </div>
                <div className="flex items-center justify-between">
                  <span className="font-medium">{LABELS[theme]}</span>
                  {isPending && (
                    <Loader2
                      className="h-4 w-4 animate-spin text-muted-foreground"
                      aria-label="Salvando"
                    />
                  )}
                  {isSelected && !isPending && (
                    <span className="text-xs font-medium text-primary">Selecionado</span>
                  )}
                </div>
              </button>
            );
          })}
        </div>
      );
    }
    ```

### Decisão DEV-1 — Surface do `/dashboard/theme` em `light` (não aplica tema do user na surface inteira)

**Problema:** AC1 diz "página `/dashboard/theme` com 3 cards". Não diz que a página inteira deve refletir o tema escolhido. Por outro lado, Story 3.2 AC2 menciona "tema aplicado consistentemente: dashboard + página pública" — interpretado em 3.2 DEV-1 (endossado pelo @po) como "vocabulário cross-surface uniforme", não "cada surface aplica o tema do user".

**Resolução:** `/dashboard/theme` (e todo o `/dashboard/*`) mantém `data-theme="light"` herdado de `<html>` (Story 3.1). Cada card do ThemeSelector aplica seu **próprio** tema via wrapper interno (`<div data-theme={cardTheme}>` no `<ThemePreview>`). Razões:

1. **Consistência cross-Epic-3:** Stories 3.1 e 3.2 já estabeleceram o pattern (dashboard light, página pública themed).
2. **Não há `profiles.theme`:** o schema só tem `pages.theme` (FR12 = "tema por página"). Para aplicar tema "do user" no dashboard, precisaríamos:
   - (a) introduzir `profiles.theme` enum + migration + RLS update + types regen — overscope para 3.3 (deveria ser story dedicada),
   - (b) ou reusar `pages.theme` como proxy de "tema do user" — semanticamente errado (page ≠ user; um user pode ter múltiplas pages em phase 2).
3. **UX trade-off intencional:** ao deixar o dashboard light, o card "Light" é o que parece mais "integrado" à UI. Aceitável — o usuário entende que está vendo previews dos 3 temas, não o tema do dashboard em si.

**Alternativa rejeitada:** aplicar `<div data-theme={page.theme}>` como wrapper de `/dashboard/theme` para que a surface inteira reflita o tema atualmente salvo. **Custo:** quebra a consistência com `/dashboard/profile`, `/dashboard/links`, etc. (que continuariam light). **Inconsistência cognitiva:** o user só veria "seu tema" em UMA tela do dashboard. **Decisão:** rejeitar; promover a story dedicada `STORY-3.x-DASHBOARD-THEME` se @po quiser dashboard themed pós-MVP.

### Decisão DEV-2 — Estratégia de preview: Server Component `<ThemePreview>` em vez de iframe

**Problema:** AC3 admite "iframe ou Server Component isolado". Trade-offs:

| Critério           | Iframe                                                                     | Server Component isolado                                     |
| ------------------ | -------------------------------------------------------------------------- | ------------------------------------------------------------ |
| Isolamento de CSS  | Total (documento separado)                                                 | Cascade via `<div data-theme=...>` (já provado em Story 3.2) |
| Performance        | 1 request extra por preview (3 iframes ⇒ 3 requests) ou 1 com search param | 0 requests; render inline                                    |
| Routing necessário | Sim — rota `/api/theme-preview?theme=X` ou similar                         | Não — componente puro                                        |
| Fidelidade visual  | Alta (renderiza `<PublicPage>` real)                                       | Média (facsimile compacto)                                   |
| Complexidade       | Alta (CSP, sandbox, refresh handling)                                      | Baixa (componente declarativo)                               |

**Resolução:** **Server Component isolado** (`<ThemePreview>`). Razões:

1. **Story 3.2 já provou** que `<div data-theme={page.theme}>` aplica o tema corretamente via CSS cascade (PublicPage wrapper).
2. **Não precisamos da fidelidade total** — o preview é thumbnail (~200×280px). Render scaled de `<PublicPage>` (que usa `min-h-screen mx-auto max-w-md py-8`) exigiria CSS transforms problemáticos.
3. **Iframe adicionaria complexidade desproporcional** — precisaria de uma rota dedicada, e refresh state quando o user troca de tema (re-render do iframe).
4. **`<ThemePreview>` é facsimile fiel o suficiente** — usa os mesmos tokens (`bg-background`, `text-foreground`, `border-border`, `bg-card`, `text-card-foreground`, `text-muted-foreground`) que `<PublicPage>` consome; visual proximamente correto.

**Alternativa rejeitada 1:** renderizar `<PublicPage>` direto com `transform: scale(0.4)` + `transform-origin: top left`. **Custo:** CSS transform sobrepõe a fluidez do layout, quebra hit-testing, performance penalty em mobile. **Decisão:** rejeitar.

**Alternativa rejeitada 2:** iframe com rota `/api/theme-preview/[t]/page.tsx`. **Custo:** rota extra, refresh handling, sandbox CSP. **Decisão:** rejeitar.

### Decisão DEV-3 — RLS via `.eq('profile_id', user.id)` sem filtro explícito por `pages.id`

**Problema:** o pattern canônico em `server/links/actions.ts:75-92` resolve o `page_id` primeiro (`SELECT id FROM pages WHERE profile_id = user.id`), depois faz `UPDATE links WHERE page_id = ?`. Para `updateTheme`, temos a opção mais direta: `UPDATE pages SET theme=? WHERE profile_id = auth.uid()` — sem pre-SELECT.

**Resolução:** uma única query. Razões:

1. **Relação 1:1 `profiles → pages`** (Story 2.2 — trigger AFTER INSERT ON auth.users cria uma row em `pages` por user). Não há ambiguidade — `profile_id = user.id` resolve para exatamente 0 ou 1 row.
2. **RLS `pages_update_own`** já filtra a row do owner — a query é defense in depth.
3. **`.single()`** garante exit precoce se zero rows (RLS bloqueou OU page não existe ainda — improvável pós-trigger, mas defensivo).
4. **Performance:** 1 query em vez de 2 (50% redução de round-trips para esta Server Action).

**Padrão similar:** `server/profile/actions.ts:51-56` faz `UPDATE profiles SET username=? WHERE id = user.id` — mesma estratégia "RLS + single query".

### Decisão DEV-4 — Optimistic UI + rollback + `useTransition`

**Problema:** ao clicar em um card, o user espera feedback imediato. Padrões possíveis:

| Padrão                             | Latência percebida               | Complexidade |
| ---------------------------------- | -------------------------------- | ------------ |
| Pessimista (espera Server Action)  | ~300-500ms (P95 arch L2189)      | Baixa        |
| Optimistic + rollback (`useState`) | ~0ms                             | Média        |
| `useOptimistic` (Next 16/React 19) | ~0ms + integrado com transitions | Média/Alta   |

**Resolução:** `useState` + `useTransition` (padrão verbatim Story 2.6 `components/links/LinkList.tsx:48-62`). Razões:

1. **Precedente sancionado** — Story 2.6 PASS pelo @qa (gate file `2.6-reorder-drag-drop.yml`). Pattern compatível com Next 16.
2. **`useOptimistic` é mais elegante** mas exige formulários ou Server Actions encapsulados em `<form>`. ThemeSelector usa `<button>` com `onClick`, não `<form action={...}>` — `useTransition` é mais natural.
3. **Rollback explícito** (`setSelected(previous)` em erro) é fácil de testar e debug — o teste `c) erro do server reverte seleção` cobre isso.
4. **`useTransition` evita bloqueio** do main thread durante a Server Action (sobretudo importante se @qa testar a UX em condição de rede lenta).

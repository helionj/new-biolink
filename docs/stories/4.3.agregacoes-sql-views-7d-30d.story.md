### Decisões & Deviations (Constitution Art. IV — default fundamentado + fonte; NÃO inventar)

- **DEV-1 — Naming da migration (`0009_views_aggregations.sql`):** `schema-design.md §10` prescreve `YYYYMMDDHHMMSS_*.sql` (Supabase CLI default). `architecture.md §L1644` referencia este arquivo especificamente como `0005_views_aggregations.sql` (off-by-N, foi escrito quando a numeração era diferente). **Realidade do repo:** `000N_*.sql` desde 0001/.../0008. → **Decisão:** seguir convenção real do repo: `supabase/migrations/0009_views_aggregations.sql` + `supabase/rollbacks/0009_views_aggregations_rollback.sql`. Drift doc↔repo documentado (deviation idêntica a 2.2 DEV-1, 2.3 DEV-1, 4.1 DEV-1, 4.2 DEV-1 — todas fechadas APPROVED low nos gates). **Não-bloqueante.**

- **DEV-2 — `WITH (security_invoker = true)` em todas as 4 views — CRÍTICO PARA SEGURANÇA:** Postgres views por default rodam com permissões do **criador** (sintaxe `SECURITY DEFINER`-like — quando o owner é `postgres` ou `supabase_admin`, **RLS das tabelas-base é IGNORADA**). Em PG 15+, `WITH (security_invoker = true)` força a view a usar permissões do **caller** → RLS de `click_events_select_own` / `page_views_select_own` é aplicada corretamente. **Sem esta cláusula, owner consegue ler views de outros usuários — vazamento de PII por engano de configuração.** → **Decisão:** **OBRIGATÓRIO** `WITH (security_invoker = true)` em cada `CREATE VIEW` (Task 1.2-1.5). **Validação central (Task 6.3 cenário (p)):** integration test compara `admin` (bypass RLS) vs `sessions.alice.client` (com RLS) — devem retornar conjuntos DIFERENTES de rows agregadas (admin vê tudo, alice vê apenas suas). Se conjuntos forem IGUAIS, `security_invoker` está incorreto e a story FALHA gate. **Não-bloqueante para draft; bloqueante para implementação se omitido.** **Flagged para gate @architect.** _Referência:_ https://www.postgresql.org/docs/15/sql-createview.html#SQL-CREATEVIEW-SECURITY (security_invoker doc).

- **DEV-3 — `SECURITY INVOKER STABLE` nas 2 helper functions:** Postgres functions têm 3 opções: `SECURITY INVOKER` (caller's perms, RLS aplicada), `SECURITY DEFINER` (creator's perms, RLS bypass — usado por `reorder_links` 0005 e `on_auth_user_created` 0002 onde bypass é semanticamente correto). **Para `get_*_series`, RLS DEVE ser aplicada** (mesma razão de DEV-2 — vazamento de PII por engano). → **Decisão:** `SECURITY INVOKER` obrigatório nas 2 funções (Task 3.1, 3.2). **STABLE** porque dependem de `now()` (não pode ser IMMUTABLE; STABLE permite cache dentro de single statement). **LANGUAGE sql** (não plpgsql) — função one-liner sem variáveis nem branching, `LANGUAGE sql` é mais simples e Postgres inline-otimiza. **Não-bloqueante.** _Referência:_ https://www.postgresql.org/docs/current/sql-createfunction.html#SQL-CREATEFUNCTION-SECURITY (security clause doc).

- **DEV-4 — Default `p_days = 7` nas helper functions:** PRD AC3 verbatim ("Função SQL helper para retornar séries temporais") **não especifica** valor default. Alternativa rejeitada: sem default (caller sempre passa explicitamente — mais conservador mas mais verboso na UI). → **Decisão:** `DEFAULT 7` espelha o "primeiro caso" de uso da 4.4 (gráfico 7d default + toggle 30d, `architecture.md §Components #7 L535-545`). **Limitação PostgREST:** alguns clientes PostgREST exigem que **todos** os args sejam passados explicitamente mesmo com default no schema (verificar empiricamente em Task 5.10; se exigir, documentar mas manter default para chamadas SQL diretas). **Ratificar com @po em validate-draft.** **Não-bloqueante; ajustável.**

- **DEV-5 — Sparse series (sem gap-filling):** PRD AC3 menciona "array de `{date, count}`" — não exige array contínuo (dense series com zeros). Alternativa rejeitada: gap-fill server-side via `generate_series(now()::date - p_days, now()::date, '1 day'::interval)` LEFT JOIN — adiciona complexidade SQL + ~3-5× mais linhas no payload por janela (30d com 1 dia ativo retorna 30 rows com 29 zeros). → **Decisão:** sparse series — função retorna apenas dias com >= 1 evento. Gap-fill é responsabilidade da UI 4.4 em JS (mais barato CPU-wise, permite timezone do cliente). **Documentar em COMMENT da função** (Task 3.3). **Não-bloqueante.**

- **DEV-6 — AC2 estratégia documentada por referência (não-duplicada):** PRD AC2 verbatim ("Estratégia documentada (views regulares para MVP — refresh sob demanda; materialized views deferidas)") **JÁ existe** em 2 docs: `architecture.md §Data Models §Aggregation Views L356-365` (decisão principal) + `schema-design.md §4 Views §Materialized Views L655-657` (referência cruzada). - **DEV-7 — Sem GRANT/REVOKE customizado em views:** Postgres + Supabase: roles `authenticated` e `anon` herdam `SELECT` sobre objetos em schema `public` por default (Supabase setup). `security_invoker=true` (DEV-2) já garante que RLS das tabelas-base é a única gate de acesso. Adicionar `REVOKE SELECT ON link_clicks_7d FROM anon` seria redundante (anon não consegue ler nada via RLS) e quebra a simetria com `click_events`/`page_views` que **não** têm REVOKE customizado. → **Decisão:** zero GRANT/REVOKE custom. Defense é 100% via RLS + `security_invoker`. **Não-bloqueante.**

- **DEV-9 — Boundary semântica de `>=`:** filtro `WHERE clicked_at >= now() - interval '7 days'` é **inclusivo** no limite (event exatamente 7 dias atrás entra na 7d view; event 7 dias e 1 segundo atrás NÃO entra). Comportamento Postgres canônico mas vale documentar para 4.4 saber. ### Helper functions canônicas (DEV-3, DEV-4, DEV-5)

```sql
-- =============================================================================
-- Function: get_page_views_series(p_page_id uuid, p_days int)
-- Returns: TABLE(day date, count bigint) — sparse (dias zerados omitidos)
-- =============================================================================
CREATE OR REPLACE FUNCTION get_page_views_series(p_page_id uuid, p_days int DEFAULT 7)
RETURNS TABLE(day date, count bigint)
LANGUAGE sql
SECURITY INVOKER
STABLE
AS $$
  SELECT date_trunc('day', viewed_at)::date AS day,
         count(*)::bigint AS count
  FROM page_views
  WHERE page_id = p_page_id
    AND viewed_at >= now() - (p_days || ' days')::interval
  GROUP BY date_trunc('day', viewed_at)
  ORDER BY day ASC;
$$;

COMMENT ON FUNCTION get_page_views_series(uuid, int) IS
  'Série temporal de page views por dia, últimos N dias (FR11/AC3). SECURITY INVOKER respeita RLS de page_views. STABLE (depende de now()). Sparse — dias zerados omitidos; gap-fill é responsabilidade do caller (UI Story 4.4).';

-- =============================================================================
-- Function: get_link_clicks_series(p_link_id uuid, p_days int)
-- Returns: TABLE(day date, count bigint) — sparse
-- =============================================================================
CREATE OR REPLACE FUNCTION get_link_clicks_series(p_link_id uuid, p_days int DEFAULT 7)
RETURNS TABLE(day date, count bigint)
LANGUAGE sql
SECURITY INVOKER
STABLE
AS $$
  SELECT date_trunc('day', clicked_at)::date AS day,
         count(*)::bigint AS count
  FROM click_events
  WHERE link_id = p_link_id
    AND clicked_at >= now() - (p_days || ' days')::interval
  GROUP BY date_trunc('day', clicked_at)
  ORDER BY day ASC;
$$;

COMMENT ON FUNCTION get_link_clicks_series(uuid, int) IS
  'Série temporal de cliques por dia em um link, últimos N dias (FR11/AC3). SECURITY INVOKER respeita RLS de click_events. STABLE. Sparse.';
```

### Estratégia RLS — defense-in-depth via `security_invoker` + RLS das tabelas-base (DEV-2, DEV-3, DEV-7)

```
Caller (sessions.alice.client)
  ↓ SELECT * FROM page_views_7d WHERE page_id = ?
  ↓ View query expanded:
  ↓   SELECT page_id, date_trunc('day', viewed_at) AS day, count(*) AS count
  ↓   FROM page_views WHERE viewed_at >= now() - '7 days' AND page_id = ?
  ↓   GROUP BY ...
  ↓ Postgres aplica security_invoker=true → query roda como alice (não postgres)
  ↓ RLS de page_views_select_own ativa:
  ↓   USING (EXISTS (SELECT 1 FROM pages p WHERE p.id = page_id AND p.profile_id = auth.uid()))
  ↓ Se page_id pertence a alice → rows visíveis → agregação correta
  ↓ Se page_id pertence a bob (alice tentando ler) → 0 rows visíveis → resposta vazia
  ↓ Se anon → auth.uid() IS NULL → predicado falha → 0 rows
```

**Insight crítico:** o agregado `count(*)` opera sobre as rows **visíveis** por RLS — alice recebe `count(*)` apenas dos events que ela pode ler. Sem `security_invoker=true`, alice receberia `count(*)` de TODOS os events (incluindo bob) — **vazamento severo de PII analytics**. Validação central em Task 6.3 cenário (p).

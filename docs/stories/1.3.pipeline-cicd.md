> **Rationale:** Story de **Infra/CI/CD/Deploy** (GitHub Actions + Vercel + Husky + Supabase Branching). Per `story-tmpl.yaml` mapping → executor `@devops`, quality_gate `@architect`. Per `.claude/rules/agent-authority.md` linhas 8-12, CI/CD pipeline management é **EXCLUSIVO** de `@devops` (Gage) — `@dev` não pode escrever workflows. Quality gate tools: `pnpm typecheck`, `pnpm lint`, `pnpm build` (regressão zero do estado atual), validação sintática dos YAMLs (`yamllint` ou parse via `act`/CI dry-run), e execução manual dos hooks Husky (pre-commit + pre-push) localmente. Complexity **M (Medium)** — 4-6h: 2 workflow files, 2 Husky hooks, Vitest scaffold (não-trivial mas mínimo), secrets em 2 plataformas (GitHub Actions + Vercel), validação end-to-end via PR de teste real.

## Story

**As a** desenvolvedor,
**I want** GitHub Actions executando lint/typecheck/test/build em todo PR e Vercel fazendo auto-deploy de `main`,
**so that** quality gates sejam impostos antes do merge e a produção reflita `main` em até 5 minutos.

3. **Status checks bloqueiam merge** em PRs que falham qualquer job — branch protection rule configurada em GitHub no repo `helionj/new-biolink` exigindo os **6 jobs** verdes (lint, typecheck, test-unit, test-components, build, gitleaks, audit; test-integration deferido) antes de "Merge pull request" estar disponível.

**Workflow trigger pattern:**

```yaml
on:
```

**Jobs paralelos (architecture §1825-1961) — implementar literal:**

| Job                | needs                                       | Runs on       | Skip condition                            |
| ------------------ | ------------------------------------------- | ------------- | ----------------------------------------- |
| `install`          | —                                           | ubuntu-latest | nunca                                     |

| `test-unit`        | install                                     | ubuntu-latest | nunca                                     |
| `test-components`  | install                                     | ubuntu-latest | nunca                                     |
| `test-integration` | install                                     | ubuntu-latest | `if: github.event_name == 'pull_request'` |
| `build`            | lint, typecheck, test-unit, test-components | ubuntu-latest | nunca                                     |
| `gitleaks`         | —                                           | ubuntu-latest | nunca (fetch-depth: 0)                    |

**Pattern por job (exceto install/gitleaks):**

```yaml
job-name:
  needs: install
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - uses: pnpm/action-setup@v3
      with: { version: '${{ env.PNPM_VERSION }}' }
    - uses: actions/setup-node@v4
      with: { node-version: '${{ env.NODE_VERSION }}', cache: 'pnpm' }
    - run: pnpm install --frozen-lockfile
    - run: pnpm <command>
```

**Pattern test-integration (architecture §1883-1917) — implementação literal:**

```yaml
test-integration:
  needs: install
  runs-on: ubuntu-latest
  if: github.event_name == 'pull_request'
  steps:
    - uses: actions/checkout@v4
    - uses: pnpm/action-setup@v3
      with: { version: '${{ env.PNPM_VERSION }}' }
    - uses: actions/setup-node@v4
      with: { node-version: '${{ env.NODE_VERSION }}', cache: 'pnpm' }
    - run: pnpm install --frozen-lockfile
    - uses: supabase/setup-cli@v1
    - name: Create Supabase Branch
      env:
        SUPABASE_ACCESS_TOKEN: ${{ secrets.SUPABASE_ACCESS_TOKEN }}
      run: |
        BRANCH_NAME="pr-${{ github.event.pull_request.number }}"
        supabase branches create "$BRANCH_NAME" --project-ref ${{ secrets.SUPABASE_PROJECT_REF }} || \
          supabase branches get "$BRANCH_NAME" --project-ref ${{ secrets.SUPABASE_PROJECT_REF }}
        BRANCH_URL=$(supabase branches get "$BRANCH_NAME" --project-ref ${{ secrets.SUPABASE_PROJECT_REF }} -o json | jq -r '.db_url')
        echo "SUPABASE_DB_URL=$BRANCH_URL" >> $GITHUB_ENV
    - name: Apply migrations
      run: supabase db push --db-url "$SUPABASE_DB_URL"
    - name: Run integration tests
      env:
        SUPABASE_DB_URL: ${{ env.SUPABASE_DB_URL }}
        HASH_SALT: 'ci-fixed-salt-32-chars-minimum-aaaaaa'
      run: pnpm test:integration
    - name: Cleanup Supabase Branch
      if: always()
      env:
        SUPABASE_ACCESS_TOKEN: ${{ secrets.SUPABASE_ACCESS_TOKEN }}
      run: |
        supabase branches delete "pr-${{ github.event.pull_request.number }}" \
          --project-ref ${{ secrets.SUPABASE_PROJECT_REF }} || true
```

### Security Considerations

[Source: docs/architecture.md §Security and Performance, linhas 2089-2110]

- **0 secrets versionados (NFR10):** gitleaks pre-commit (local, opcional) + CI (canônico, bloqueante).
- **`SUPABASE_SERVICE_ROLE_KEY` em CI:** usado **apenas** no job `build` (env injetado). Não vaza para job test-integration (que usa branch isolado com seu próprio db_url). Cuidado: nunca declarar em job que faça `echo $SECRET` — workflow só usa via `env:` injection.
- **Service role em Vercel:** marcar como `Sensitive` (Vercel oferece "Sensitive" flag em Env Vars desde 2024) se UI permitir.
- **Branch previews públicos (AC5):** Disable Vercel Authentication para acessibilidade pública dos previews. Trade-off conhecido: previews são públicos durante MVP open-source. Para features sensíveis pré-launch, esconder atrás de feature flag.
- **gitleaks ignora `.env.example`** (placeholders sem valor), `docs/*.md` (referências documentais sem valores reais), `pnpm-lock.yaml` (hashes/integridade, não secrets).
- **`SUPABASE_ACCESS_TOKEN` no GHA:** Personal Access Token do usuário — escopo padrão permite branches CRUD. Rotacionar via `supabase.com/dashboard/account/tokens` se vazar suspeita.

### Technical Constraints

- **Auto-deploy em `main` exige branch protection NÃO incluir "Require approvals"** se o objetivo for que merge pelo próprio dono dispare deploy imediato. PRD pede "≥ 1 deploy/semana" e "produção reflete main em até 5 min" — política de approvals fica opcional, mas no MVP solo, sem approvals.
- **Custom domain ausente (NFR18):** Vercel-assigned URL é a produção do MVP. Configuração de Apex/custom domain → Phase 2.
- **Sem Sentry/Datadog (NFR5 + budget):** logs vão para Vercel Logs (built-in) + Supabase Dashboard. Não adicionar APM neste epic.
- **Não criar scripts `seed:demo` aqui:** PRD §Test convenience menciona seed; entra junto com Story 1.4 quando o schema existe.
- **Pre-push roda `pnpm typecheck`, não `pnpm test`:** decisão de manter pre-push leve. Tests rápidos confiam no CI; pre-push só protege contra erro de tipo trivial.
- **`audit` job pode falhar em CRITICAL** após bumps do Dependabot futuro — política: hotfix story imediato. Documentar no Dev Notes da story que introduzir falha.
- **`passWithNoTests` é temporário:** quando Story 1.4 adicionar primeiro RLS test e 1.8 adicionar primeiro component test, manter a flag para evitar quebrar CI quando algum project ficar sem testes em PR não-relacionado. Stories futuras podem promover para `passWithNoTests: false` quando todos os 3 projects tiverem ≥ 1 teste.

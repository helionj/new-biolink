Primeira interação real com `react-hook-form` + Zod resolver no projeto.

## Story

**As a** visitante do BioLink,
**I want** me cadastrar com email/senha + escolher meu username, fazer login subsequente e logout do dashboard,
**so that** eu tenha uma conta autenticada que produz um `profile` válido (via trigger `on_auth_user_created` de 1.4) e possa começar a configurar minha página `/@username` nas próximas stories.

## Acceptance Criteria

1. **Página `/signup`** (`app/(auth)/signup/page.tsx`) renderiza `<SignupForm />` (Client Component) com 5 campos validados client-side via **react-hook-form + @hookform/resolvers/zod** usando schema `SignUpInput` em `lib/validators/auth.ts`: (a) `email` (Zod `.email()` PT-BR error); (b) `password` (Zod `.min(8, 'A senha precisa ter no mínimo 8 caracteres')`); (c) `confirmPassword` (validado via `.refine((data) => data.password === data.confirmPassword, { message: 'As senhas não coincidem', path: ['confirmPassword'] })`); (d) `username` (Zod `.regex(/^[a-z0-9-]{3,30}$/, 'Use 3 a 30 caracteres entre a-z, 0-9 e hífen')` — espelha CHECK constraint da migration 0002 + check adicional contra `RESERVED_USERNAMES` de `lib/reserved-usernames.ts`); (e) `acceptTerms` (Zod `.literal(true, 'Aceite os termos para continuar')`). Botão "Criar conta" desabilitado enquanto `isSubmitting`. **PRD AC1 usa "slug" — neste codebase, o termo canônico é `username`** (alinha com `profiles.username`, `raw_user_meta_data.username` consumido pelo trigger 1.4); ver Project Structure Notes #1.

2. **Página `/login`** (`app/(auth)/login/page.tsx`) renderiza `<LoginForm />` com 2 campos (email + password) validados via `SignInInput` Zod schema (`email` válido + `password` não-vazio — sem mínimo de chars no login para evitar dar pista a atacante). Link "Esqueci a senha" presente apontando para `/reset-password` (rota será implementada em Story 1.6 — neste momento, o `<Link>` aponta para `/reset-password` mesmo que a página retorne 404 hoje; é aceitável e documentado). Botão "Entrar" desabilitado enquanto submitting.

3. **Logout disponível no `/dashboard`** via componente `<LogoutButton />` (Client Component, mínimo no MVP — botão simples que chama Server Action `signOut`). `app/dashboard/page.tsx` é um **placeholder mínimo** (não o dashboard final) que exibe: (a) email do usuário autenticado (`user.email`), (b) `<EmailVerificationBanner />` quando `user.email_confirmed_at` for null, (c) `<LogoutButton />`. Após logout: clear de sessão Supabase (cookies HTTP-only) + `redirect('/')`. Polish completo do shell (sidebar, UserMenu dropdown, navegação) é escopo de **Story 1.9 (Landing) e stories de Epic 2** — aqui é o mínimo para satisfazer AC3.

4. **Erros de auth renderizados como Toast** via `sonner` (shadcn-toast oficial atual). `<Toaster />` montado uma única vez em `app/layout.tsx` (root layout). Server Actions `signUp`/`signIn` retornam `ActionResult<void>` (`lib/result.ts`); UI verifica `res.ok` e dispara `toast.error(res.error)` no `false`. Cenários cobertos: (a) credenciais inválidas (`signIn` → "Email ou senha incorretos"), (b) email já em uso (`signUp` Supabase error mapeado → "Este email já está cadastrado"), (c) username já em uso (`signUp` checa via `SELECT 1 FROM profiles WHERE username=?` antes de `auth.signUp` → "Este username já está em uso"), (d) username reservado (rejeitado client-side via Zod refine + server-side via Server Action defensiva), (e) erro genérico Supabase ("Erro ao processar. Tente novamente"). **fieldErrors** opcionais retornam para o form para destacar campo específico (ver `ActionResult.fieldErrors`).

5. **Após signup com sucesso**, Server Action `signUp` faz: (i) `supabase.auth.signUp({ email, password, options: { data: { username } } })` — passa username via `raw_user_meta_data` que o trigger 1.4 (`on_auth_user_created`) lê e usa para criar a row em `profiles` automaticamente; (ii) `redirect('/dashboard')` server-side (Next.js `redirect` de `next/navigation`). O dashboard placeholder exibe o `<EmailVerificationBanner />` em PT-BR ("Confirme seu email para garantir o acesso à sua conta") quando `auth.users.email_confirmed_at IS NULL`. **Decisão de config Supabase:** `Confirm email` em **Auth → Providers → Email** do projeto `biolink-dev` é **desabilitado** para Story 1.5 (permite auto-session pós-signup, satisfazendo AC5 redirect direto a `/dashboard`); Story 1.6 reativa esse setting + implementa `/auth/callback` para handling do link do email. Documentar essa decisão + plano de toggle em `docs/dev-setup.md §13` (nova seção).

6. **Tradução PT-BR** em todas as strings visíveis: labels dos campos, placeholders, botões, mensagens de erro Zod (custom messages), toasts, banner de email, link "Esqueci a senha". Convenção: literais inline em PT-BR per arch §Coding Standards "i18n PT-BR-only no MVP" (linha 2402) — **sem** next-intl, **sem** chaves dinâmicas. Aceitar duplicação eventual em troca de zero overhead de internacionalização (revisitar em Phase 2).

7. **Middleware mínimo de redirect** (`middleware.ts` na raiz) cobre apenas as duas redirects necessárias para fechar o loop de AC2/AC5: (a) usuário autenticado em `/signup` ou `/login` → redirect para `/dashboard`; (b) guest em `/dashboard` → redirect para `/login?next=/dashboard`. **Não cobre todas as rotas privadas** (Story 1.7 expande para `/dashboard/*` completo + edge cases). Implementação alinhada a arch §Routing > Protected Route Pattern (linhas 1178-1229) mas com matcher reduzido para `/signup`, `/login`, `/dashboard` apenas — comentário inline documenta o escopo limitado e cross-ref a Story 1.7.

  - [x] 5.1 Criar `middleware.ts` na raiz do projeto baseado em arch §Routing > Protected Route Pattern (linhas 1178-1229) com matcher REDUZIDO. Implementação:

    ```typescript
    import { type NextRequest, NextResponse } from 'next/server';
    import { createServerClient } from '@supabase/ssr';
    import { env } from '@/lib/env';

    const PROTECTED_PATHS = ['/dashboard'];
    const AUTH_PAGES = ['/login', '/signup'];

    export async function middleware(req: NextRequest) {
      const res = NextResponse.next();
      const supabase = createServerClient(
        env.NEXT_PUBLIC_SUPABASE_URL,
        env.NEXT_PUBLIC_SUPABASE_ANON_KEY,
        {
          cookies: {
            getAll: () => req.cookies.getAll(),
            setAll: (toSet) =>
              toSet.forEach(({ name, value, options }) => res.cookies.set(name, value, options)),
          },
        },
      );
      const {
        data: { user },
      } = await supabase.auth.getUser();
      const path = req.nextUrl.pathname;

      if (PROTECTED_PATHS.some((p) => path.startsWith(p)) && !user) {
        const url = req.nextUrl.clone();
        url.pathname = '/login';
        url.searchParams.set('next', path);
        return NextResponse.redirect(url);
      }

      if (AUTH_PAGES.some((p) => path.startsWith(p)) && user) {
        const url = req.nextUrl.clone();
        url.pathname = '/dashboard';
        return NextResponse.redirect(url);
      }

      return res;
    }

    // Story 1.7 expandirá o matcher para `/((?!_next/static|...).*)` cobrindo todas
    // as rotas privadas. Aqui é deliberadamente reduzido a /signup, /login, /dashboard
    // para minimizar surface de bugs no MVP de auth UI.
    export const config = {
      matcher: ['/signup', '/login', '/dashboard/:path*'],
    };
    ```

**Padrão canônico** (per arch §Frontend Services Layer linhas 1300-1368, exemplo `createLink`):

```typescript
'use server';

import { z } from 'zod';
import { redirect } from 'next/navigation';
import { createClient } from '@/lib/supabase/server';
import type { ActionResult } from '@/lib/result';
import { SignUpInput } from '@/lib/validators/auth';

export async function signUp(raw: SignUpInput): Promise<ActionResult<void>> {
  const parsed = SignUpInput.safeParse(raw);
  if (!parsed.success) {
    return {
      ok: false,
      error: 'Entrada inválida',
      fieldErrors: parsed.error.flatten().fieldErrors as Record<string, string>,
    };
  }
  const { email, password, username } = parsed.data;
  const supabase = await createClient();

  // Pre-check de username (UX-friendly antes de invocar Auth)
  const { data: existing } = await supabase
    .from('profiles')
    .select('id')
    .eq('username', username)
    .maybeSingle();
  if (existing) {
    return {
      ok: false,
      error: 'Este username já está em uso',
      fieldErrors: { username: 'Este username já está em uso' },
    };
  }

  const { error } = await supabase.auth.signUp({
    email,
    password,
    options: { data: { username } },
  });
  if (error) {
    if (error.message.includes('User already registered')) {
      return {
        ok: false,
        error: 'Este email já está cadastrado',
        fieldErrors: { email: 'Este email já está cadastrado' },
      };
    }
    return { ok: false, error: 'Erro ao criar conta. Tente novamente' };
  }

  redirect('/dashboard');
}
```

### Form Pattern — react-hook-form + Zod resolver

[Source: docs/architecture.md §State Management > Forms, linhas 1124-1126; §Coding Standards linha 2392]

Pattern canônico que SignupForm e LoginForm devem seguir:

```typescript
'use client';

import { useForm } from 'react-hook-form';
import { zodResolver } from '@hookform/resolvers/zod';
import { toast } from 'sonner';
import { Button } from '@/components/ui/button';
import { Input } from '@/components/ui/input';
import { Label } from '@/components/ui/label';
import { Form, FormField, FormItem, FormLabel, FormControl, FormMessage } from '@/components/ui/form';
import { SignUpInput } from '@/lib/validators/auth';
import { signUp } from '@/server/auth/actions';

export function SignupForm() {
  const form = useForm<SignUpInput>({
    resolver: zodResolver(SignUpInput),
    defaultValues: {
      email: '',
      password: '',
      confirmPassword: '',
      username: '',
      acceptTerms: false,
    },
  });

  async function onSubmit(values: SignUpInput) {
    const res = await signUp(values);
    if (!res?.ok) {
      toast.error(res?.error ?? 'Erro ao criar conta');
      // Se houver fieldErrors, espalhar via form.setError
      if (res?.fieldErrors) {
        for (const [field, message] of Object.entries(res.fieldErrors)) {
          form.setError(field as keyof SignUpInput, { message: String(message) });
        }
      }
    }
    // Em sucesso, Server Action chamou redirect() server-side — UI não retorna nada visível.
  }

  return (
    <Form {...form}>
      <form onSubmit={form.handleSubmit(onSubmit)} className="space-y-4">
        {/* 5 campos com FormField/FormItem/FormLabel/FormControl/FormMessage */}
        <Button type="submit" disabled={form.formState.isSubmitting}>
          Criar conta
        </Button>
      </form>
    </Form>
  );
}
```

### Technical Constraints

- **Next.js 16 + React 19:** `'use server'` Server Actions canônicos; `redirect()` de `next/navigation` arremessa `NEXT_REDIRECT` error (testes precisam capturar via try/catch ou `expect.rejects`).
- **shadcn/ui + Tailwind 4:** shadcn CLI suporta TW 4 nativamente desde 2025 — usa `@theme inline` em `app/globals.css` (já presente no projeto). NÃO criar `tailwind.config.ts` — projeto é CSS-first per arch §Tech Stack tabela linha 170. Validar com `pnpm dev` que o Button renderiza corretamente após `add`.
- **Supabase Auth:** `signUp` retorna `{ user, session, error }`; com Confirm Email OFF, `session` é estabelecida automaticamente + cookies set via `@supabase/ssr` server client. Trigger `on_auth_user_created` (Story 1.4) lê `raw_user_meta_data->>'username'` — passar via `options: { data: { username } }`.
- **Service-role isolation (arch §Coding Standards linha 2395):** `lib/supabase/admin.ts` usado APENAS em integration tests (cleanup, validação). NÃO usar em Server Actions desta story (todas operam no anon path com session cookies — RLS aware).
- **Env via Zod (arch §Coding Standards linha 2396):** middleware usa `env.NEXT_PUBLIC_SUPABASE_URL` / `env.NEXT_PUBLIC_SUPABASE_ANON_KEY` de `@/lib/env` — NÃO `process.env.X` direto.
- **Strict TypeScript:** `noUncheckedIndexedAccess` ativo — atenção a iterações em `Object.entries(res.fieldErrors)` (valor pode ser `undefined`; assertar com `String(message)` ou guard).
- **i18n PT-BR (arch §Coding Standards linha 2402):** literais inline ou `lib/strings.ts` (constants) — sem next-intl, sem chaves dinâmicas. Esta story usa literais; refatorar quando 1 string for usada em 3+ lugares.
- **Server-First (arch §Coding Standards linha 2390):** `app/(auth)/signup/page.tsx` e `app/(auth)/login/page.tsx` são Server Components; SignupForm/LoginForm/LogoutButton são `'use client'` justificadamente (forms interativos com state local).
- **Confirmação dupla em destrutivos (arch §Coding Standards linha 2401):** logout no MVP NÃO requer modal de confirmação — é reversível (refazer login). Story 4.5 (`deleteAccount`) ESSA sim requer modal.

### Project Structure Notes

Discrepâncias / decisões tomadas durante o draft:

1. **PRD AC1 cita `slug` como nome do campo de identificador público.** Em todo o resto do projeto (arch §Data Models > Profile, Story 1.4 schema, trigger `on_auth_user_created` que lê `raw_user_meta_data->>'username'`), o nome canônico é `username`. **Decisão:** usar `username` consistentemente em código, validators, UI e testes — alinha com `profiles.username` + `auth.users.raw_user_meta_data.username`. Documentar no Change Log; rotular o input no form com label "Username" + helper text "Seu @ público (3-30 caracteres, a-z, 0-9 e hífen)". Mantém PRD AC1 satisfeito em **espírito** (campo de identificador escolhido pelo usuário no signup) com nomenclatura corrigida.

2. **PRD AC1 não menciona pre-check de username no Server Action**, apenas validação client-side. Adicionei `SELECT 1 FROM profiles WHERE username=?` antes de `auth.signUp` para UX melhor (evita criar `auth.users` com email + falhar no trigger por username duplicado). Trade-off explícito: adiciona 1 round-trip ao DB; race window pequena entre check e insert (mitigada por UNIQUE constraint em `profiles.username` que rejeitaria via SQLSTATE 23505 — mensagem amigável fallback).

3. **PRD AC5 implica session imediata pós-signup** ("usuário é redirecionado para `/dashboard` com banner pedindo confirmação de email"). Isso só funciona se **Confirm Email** estiver desabilitado em Supabase Auth (caso contrário, signUp retorna `{ user, session: null }` e middleware loop kicks). **Decisão (Task 7.1):** desabilitar Confirm Email em `biolink-dev` para esta story — Story 1.6 reativa quando `/auth/callback` estiver wired. Documentar em `docs/dev-setup.md §13`. **Risco:** dev/prod parity — em produção (`biolink-prod` ainda não criado) Confirm Email DEVE estar enabled antes do release público; Story 1.6 garante isso.

4. **Cross-story coupling com 1.6 (Reset Password) + 1.7 (Middleware) + 1.8 (Design System):**
   - Link "Esqueci a senha" no `/login` aponta para `/reset-password` que retorna 404 hoje (rota criada em 1.6). Aceitável — link funcional após 1.6.
   - Middleware nesta story é mínimo (matcher `['/signup', '/login', '/dashboard/:path*']`) por design — Story 1.7 expande para todas as rotas privadas + edge cases (refresh token, session expirada, etc.).
   - shadcn primitives instaladas aqui (Button, Input, Label, Form, Sonner) são as **5 mínimas** para 1.5; Story 1.8 instala Card, Modal, Avatar, Switch + documenta tokens completos + a11y audit.

5. **`app/dashboard/page.tsx` é um placeholder**, não o dashboard final. Stories de Epic 2+ (Links Module, Profile/Theme, Analytics) substituirão progressivamente. Marker comment inline no arquivo evita confusão para quem vier depois.

6. **`app/(auth)/layout.tsx` é leve**: apenas centralização visual mobile-first. Polish de UX (hero, illustration, loading skeletons) fica para Story 1.9 (Landing) e/ou Story 1.8.

7. **shadcn init pode reescrever `app/globals.css`**: validar (Task 1.4) que os tokens placeholder `--background`/`--foreground`/`--primary`/`--muted`/`--border`/`--radius` + bloco `[data-theme='dark']` + `[data-theme='brand']` permanecem intactos. shadcn pode adicionar tokens próprios via `@layer base` — preservar os do projeto, remover duplicatas se conflitarem. Cross-ref Story 3.1+ (Themes) que vai consolidar os tokens de tema.

9. **Tests `redirect()` pattern** (Task 6.5): Next.js Server Actions que chamam `redirect()` arremessam `NEXT_REDIRECT` digest error. Esse pattern será **reusado em todas as Server Actions de stories futuras** (createLink, updateProfile, etc. que fazem redirect). Documentar inline no test file + considerar extrair `await expectRedirect(promise)` helper em `tests/integration/helpers/server-actions.ts` — **decisão pragmática:** não extrair helper nesta story (premature; só temos 4 usages). Refatorar quando 3+ Server Actions integration tests reusarem o pattern.

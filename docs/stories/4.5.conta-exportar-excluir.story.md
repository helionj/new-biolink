## Story

**As a** usuário,
**I want** acessar `/dashboard/account` para **exportar todos os meus dados em JSON** (perfil + página + links + click_events + page_views, com warning de pseudonimização) via download de blob, e **excluir minha conta permanentemente** com confirmação por digitação do username (cascade automático em todas as tabelas user-data via `auth.users ON DELETE CASCADE` + cleanup explícito de avatares no Storage + signOut + redirect para `/` com toast),
**so that** eu retenha controle total sobre meus dados pessoais conforme LGPD (PRD §FR15+FR16, brief §LGPD-mindful) — fechando o ciclo de valor do MVP do BioLink (Epic 1 onboarding → Epic 2 conteúdo → Epic 3 design system → Epic 4 analytics + conta).

    ```typescript
    'use server';
    import type { ActionResult } from '@/lib/result';
    import { createClient } from '@/lib/supabase/server';

    export async function exportAccountData(): Promise<ActionResult<AccountExport>> {
      const supabase = await createClient();
      const {
        data: { user },
      } = await supabase.auth.getUser();

      if (!user) {
        return { ok: false, error: 'Sessão expirada. Faça login novamente.' };
      }

      // RLS aplica em TODAS as queries — owner-only data via session cookies.
      // 5 queries paralelas (Promise.all) — eficiência sem comprometer correctness.
      const [profileRes, pageRes] = await Promise.all([
        supabase.from('profiles').select('*').eq('id', user.id).maybeSingle(),
        supabase.from('pages').select('*').eq('profile_id', user.id).maybeSingle(),
      ]);

      const pageId = pageRes.data?.id ?? null;

      // links + page_views só fazem sentido se pageId existe (1:1 — trigger garante)
      const [linksRes, pageViewsRes] = await Promise.all([
        pageId
          ? supabase.from('links').select('*').eq('page_id', pageId)
          : Promise.resolve({ data: [], error: null }),
        pageId
          ? supabase.from('page_views').select('*').eq('page_id', pageId)
          : Promise.resolve({ data: [], error: null }),
      ]);

      const linkIds = (linksRes.data ?? []).map((l) => l.id);

      // click_events depende de linkIds resolvido — DEV-13: 1 round-trip extra (pattern 4.4 DEV-8)
      const clickEventsRes =
        linkIds.length > 0
          ? await supabase.from('click_events').select('*').in('link_id', linkIds)
          : { data: [], error: null };

      return {
        ok: true,
        data: {
          _meta: {
            exported_at: new Date().toISOString(),
            warning:
              'ip_hash e user_agent_hash são pseudonimização SHA-256 + salt (Story 4.1) — irreversíveis sem o salt server-side. Dados são exportados como armazenados (não há transformação adicional).',
          },
          profile: profileRes.data,
          page: pageRes.data,
          links: linksRes.data ?? [],
          click_events: clickEventsRes.data ?? [],
          page_views: pageViewsRes.data ?? [],
        },
      };
    }
    ```

  - [x] 3.4 **`deleteAccount(input)`** — Server Action com input validado + service-role para cascade:

    ```typescript
    'use server';
    import { redirect } from 'next/navigation';
    import type { ActionResult } from '@/lib/result';
    import { createClient } from '@/lib/supabase/server';
    import { createAdmin } from '@/lib/supabase/admin';
    import { DeleteAccountInput } from '@/lib/validators/account';

    export async function deleteAccount(raw: unknown): Promise<ActionResult<void>> {
      const parsed = DeleteAccountInput.safeParse(raw);
      if (!parsed.success) {
        const firstError = parsed.error.flatten().fieldErrors.confirmUsername?.[0];
        return { ok: false, error: firstError ?? 'Entrada inválida' };
      }

      const supabase = await createClient();
      const {
        data: { user },
      } = await supabase.auth.getUser();
      if (!user) {
        return { ok: false, error: 'Sessão expirada. Faça login novamente.' };
      }

      // DEV-5: defense-in-depth — load profile.username e match case-insensitive
      // (citext garante isso no DB, mas client envia string raw — fazemos check server-side).
      const { data: profile, error: profileError } = await supabase
        .from('profiles')
        .select('username')
        .eq('id', user.id)
        .single();
      if (profileError || !profile?.username) {
        return { ok: false, error: 'Não foi possível verificar seu username. Tente novamente.' };
      }

      if (parsed.data.confirmUsername.trim().toLowerCase() !== profile.username.toLowerCase()) {
        return {
          ok: false,
          error: 'Username não confere. Digite exatamente seu @ para confirmar.',
        };
      }

      // DEV-4: Storage cleanup ANTES do auth.deleteUser — avatares NÃO cascateiam
      // de auth.users (Supabase Storage não tem FK p/ auth.users; cascade SQL não alcança storage.objects).
      // List + remove é best-effort — se falhar, não bloqueia delete (DEV-15: orphan storage é menos crítico que orphan DB).
      const admin = createAdmin();
      const { data: avatarFiles } = await admin.storage.from('avatars').list(user.id);
      if (avatarFiles && avatarFiles.length > 0) {
        const paths = avatarFiles.map((f) => `${user.id}/${f.name}`);
        await admin.storage.from('avatars').remove(paths); // best-effort
      }

      // DEV-3 + DEV-9: hard-delete via admin API — cascateia profiles→pages→links→click_events→page_views
      // (cascade chain verificado em comentário 0002_profiles.sql:53).
      const { error: deleteError } = await admin.auth.admin.deleteUser(user.id);
      if (deleteError) {
        return { ok: false, error: 'Erro ao excluir conta. Tente novamente.' };
      }

      // Sessão server-side já foi invalidada pelo deleteUser; signOut limpa cookies client.
      await supabase.auth.signOut();

      // DEV-9: redirect lança um erro especial que Next 16 intercepta — NÃO retornar depois.
      // Toast acontece client-side via param na landing (DEV-16) OU client lê ActionResult e
      // dispara toast antes do router.push. Decisão consolidada: client controla navigation
      // (não usar redirect server-side) para que toast.success() execute imediatamente antes
      // de unmount + navigate. Ver Task 4.4.
      return { ok: true, data: undefined };
    }
    ```

    **DEV-9:** comentário no código justifica não-uso de `redirect()` no Server Action — client controla navigation via `router.push('/')` após mostrar toast (sonner persiste 4s across navigation; canonical pattern em projects Next 16). Workflow arch §L767-792 ordena `deleteUser → signOut → redirect`; aqui mantemos ordem mas delegamos o redirect ao client para a UX do toast funcionar.

          a.click();
          document.body.removeChild(a);
          URL.revokeObjectURL(url); // cleanup

          toast.success('Dados exportados com sucesso');
        });
      }

      return (

          <Download className="mr-2 h-4 w-4" aria-hidden="true" />

    'use client';
    import { useState } from 'react';
    import { useRouter } from 'next/navigation';
    import { useForm } from 'react-hook-form';
    import { zodResolver } from '@hookform/resolvers/zod';
    import { Trash2 } from 'lucide-react';
    import {
      AlertDialog, AlertDialogAction, AlertDialogCancel, AlertDialogContent,
      AlertDialogDescription, AlertDialogFooter, AlertDialogHeader,
      AlertDialogTitle, AlertDialogTrigger,
    } from '@/components/ui/alert-dialog';
    import { Button } from '@/components/ui/button';
    import { Input } from '@/components/ui/input';
    import { Label } from '@/components/ui/label';
    import { toast } from '@/lib/toast';
    import { deleteAccount } from '@/server/account/actions';
    import { DeleteAccountInput } from '@/lib/validators/account';

    type Props = { username: string };

    export function DeleteAccountSection({ username }: Props) {
      const router = useRouter();
      const [open, setOpen] = useState(false);
      const [isSubmitting, setIsSubmitting] = useState(false);

      const form = useForm<DeleteAccountInput>({
        resolver: zodResolver(DeleteAccountInput),
        defaultValues: { confirmUsername: '' },
      });
      const confirmValue = form.watch('confirmUsername');
      const canSubmit = confirmValue.trim().toLowerCase() === username.toLowerCase() && !isSubmitting;

      async function onSubmit(values: DeleteAccountInput) {
        setIsSubmitting(true);
        const result = await deleteAccount(values);
        if (!result.ok) {
          toast.error(result.error);
          setIsSubmitting(false);
          return;
        }
        // DEV-9 / DEV-16: client controla redirect — toast first, then navigate.
        // Sonner persists across navigation (default 4s).
        toast.success('Conta excluída');
        setOpen(false);
        router.push('/');
        router.refresh(); // garante limpeza de cache RSC autenticado
      }

      return (
        <AlertDialog open={open} onOpenChange={setOpen}>
          <AlertDialogTrigger asChild>
            <Button variant="destructive">
              <Trash2 className="mr-2 h-4 w-4" aria-hidden="true" />
              Excluir conta
            </Button>
          </AlertDialogTrigger>
          <AlertDialogContent>
            <form onSubmit={form.handleSubmit(onSubmit)}>
              <AlertDialogHeader>
                <AlertDialogTitle>Tem certeza absoluta?</AlertDialogTitle>
                <AlertDialogDescription>
                  Esta ação é <strong>permanente e irreversível</strong>. Para confirmar, digite seu username <code>@{username}</code> abaixo.
                </AlertDialogDescription>
              </AlertDialogHeader>
              <div className="my-4 space-y-2">
                <Label htmlFor="confirmUsername" className="sr-only">Digite seu username para confirmar</Label>
                <Input
                  id="confirmUsername"
                  autoComplete="off"
                  autoCorrect="off"
                  spellCheck={false}
                  placeholder={username}
                  {...form.register('confirmUsername')}
                  aria-invalid={form.formState.errors.confirmUsername ? 'true' : 'false'}
                />
                {form.formState.errors.confirmUsername ? (
                  <p className="text-xs text-destructive" role="alert">
                    {form.formState.errors.confirmUsername.message}
                  </p>
                ) : null}
              </div>
              <AlertDialogFooter>
                <AlertDialogCancel disabled={isSubmitting} type="button">Cancelar</AlertDialogCancel>
                <AlertDialogAction
                  type="submit"
                  disabled={!canSubmit}
                  className="bg-destructive text-destructive-foreground hover:bg-destructive/90"
                >
                  {isSubmitting ? 'Excluindo...' : 'Excluir permanentemente'}
                </AlertDialogAction>
              </AlertDialogFooter>
            </form>
          </AlertDialogContent>
        </AlertDialog>
      );
    }

- **DEV-1 — Caminho da página `app/dashboard/account/page.tsx`:** `architecture.md §Components #9 L566` prescreve verbatim ("`app/dashboard/account/page.tsx`"). `architecture.md §Unified Project Structure L1611` ratifica ("`account/page.tsx`"). `prd.md §Story 4.5 AC1 L611` cita "Página `/dashboard/account`". `nav-items.ts:24` já aponta para `/dashboard/account` desde Story 2.4. **Decisão:** `app/dashboard/account/page.tsx` (Server Component default). **Não-bloqueante.**

- **DEV-2 — 2 Server Actions em `server/account/actions.ts`:** `architecture.md §Server Actions L410-414` prescreve verbatim:

  ```typescript
  // server/account/actions.ts
  export async function exportAccountData(): Promise<ActionResult<AccountExport>>;
  export async function deleteAccount(input: {
    confirmUsername: string;
  }): Promise<ActionResult<void>>;
  ```

  `prd.md §Story 4.5 AC2+AC3` exige ambas. **Decisão:** materializar verbatim (zero deviation de assinatura). **Não-bloqueante.**

- **DEV-3 — Cascade chain pré-existente; nenhuma migration nova nem RLS policy nova:** `supabase/migrations/0002_profiles.sql:53` tem comentário canônico verbatim ("`ON DELETE CASCADE garante limpeza via deleteAccount Server Action — Story 4.5`"). Cascade chain verificada acima em Pré-existência. **Decisão:** uma única chamada `admin.auth.admin.deleteUser(user.id)` no Server Action — DB faz o trabalho. **Alternativa rejeitada:** DELETE manual em 5 tabelas em ordem reversa (page_views → click_events → links → pages → profiles → auth.users) — viola Constitution Art. V (re-implementar funcionalidade do DB), inverte 6 round-trips desnecessários, e cria janela de inconsistência se um falhar no meio. Cascade nativo é atômico (single transaction no Postgres). **Não-bloqueante.**

- **DEV-4 — Storage cleanup explícito de `avatars/{user.id}/`:** Supabase Storage **NÃO cascateia** a partir de `auth.users` — `storage.objects` não tem FK para `auth.users`. Sem cleanup, `avatars/{deleted_user_id}/avatar.{ext}` fica órfão (não causa bug, mas vaza storage quota — bucket `avatars` tem 1 MB por user mas N users somam GB ao longo do tempo). **Decisão:** antes de `admin.auth.admin.deleteUser()`, listar `avatars/{user_id}/` via `admin.storage.from('avatars').list(user_id)` e chamar `admin.storage.from('avatars').remove(paths)`. Best-effort (não bloqueia delete se falhar — DEV-15). **Alternativa rejeitada:** trigger SQL ON DELETE em `auth.users` que faz `DELETE FROM storage.objects WHERE ... ` — `storage.objects` tem RLS próprio e modificar via trigger é frágil (Supabase pode mudar internal schema); usar Admin API é o pattern oficial. **Não-bloqueante mas crítico p/ não vazar Storage.**

- **DEV-5 — Username confirmation server-side defense-in-depth (não confiar no client):** PRD AC3 verbatim ("Delete pede confirmação por digitação do username"). Client envia string raw — se um atacante via curl/fetch chamar a Server Action direto, pode passar qualquer `confirmUsername`. **Decisão:** server-side, após auth check, LOAD `profile.username` via session e comparar case-insensitive (`.toLowerCase()`). `profiles.username` é `citext` (case-insensitive por design, `0002_profiles.sql:66`) — comparação no app é redundante mas garante consistência mesmo se um futuro update mudar `citext` para `text`. Client (Task 5.2) também valida (UX), mas servidor é canonical. **Não-bloqueante.**

- **DEV-6 — `exportAccountData` usa client autenticado (RLS), não service-role:** Workflow do export é leitura own-data; RLS já restringe via `select_own` policies em todas as tabelas (Stories 1.4, 2.2, 2.3, 4.1, 4.2). **Decisão:** `await createClient()` (server.ts) — RLS é defesa em profundidade contra bugs futuros (e.g. se algum dia mudarmos para Realtime ou Edge Functions). Service-role é reservado para o delete (DEV-3) onde precisamos cascatear via `auth.admin.deleteUser`. **Alternativa rejeitada:** usar `createAdmin()` no export "porque é mais rápido" (RLS adiciona ~5ms por query) — viola arch §Middleware/Guards L1571 ("Service-role: usado apenas em (a) trigger de signup, (b) Route Handler de tracking, (c) deletar conta"). **Não-bloqueante.**

- **DEV-7 — Page sem `searchParams` nem URL state:** `/dashboard/account` é página de ações (export/delete), não filtragem/listagem. **Decisão:** Server Component fetch leve (apenas `profile.username` para context da modal) + 2 client components button-triggered. **Sem** loading.tsx dedicado (page sem heavy fetch — render é instantâneo). **Alternativa rejeitada:** loading.tsx skeleton — overkill para fetch de 1 row. **Não-bloqueante.**

Zod aqui é só pre-flight check de input não-vazio. **Não-bloqueante.**

- **DEV-9 — Ordem `deleteUser → signOut → redirect`:** `architecture.md §Workflow 4 L767-792` prescreve sequência verbatim:

  ```
  SA->>ADMIN: admin.deleteUser(userId)
  ...
  SA->>SA: signOut()
  SA-->>FE: { ok: true }
  FE->>FE: redirect / (toast "Conta excluída")

Pattern de arch §Workflow 4 é canônico. **Não-bloqueante.**

- **DEV-10 — Filename `biolink-export-{username}-{YYYY-MM-DD}.json`:** PRD AC2 verbatim ("download via blob") — sem prescrição de nome. **Decisão:** convenção `biolink-export-{username}-{YYYY-MM-DD}.json` (e.g. `biolink-export-helion-2026-05-28.json`). Justificativa: (a) identificável (username), (b) ordenável (YYYY-MM-DD), (c) extensão `.json` clara, (d) sem horário (privacidade — não revela hora de uso). ### Technical Constraints

- **TS strict:** `strict: true` + `noUncheckedIndexedAccess: true` (PRD §Premissas Técnicas). Arrays do export podem ser vazios — guards explícitos.
- **No premature optimization (Constitution Art. V):** sem materialized view, sem RPC custom, sem cache de export (operação rara).
- **A11y (NFR3 — WCAG 2.1 AA):** dialog tem foco trap nativo do `@base-ui/react/alert-dialog`; input do confirm tem `<Label>` + `aria-invalid` + `role="alert"` no erro.
- **PT-BR (NFR11):** todas strings PT-BR. Filename é "biolink-export-..." (não traduz produto).
- **LGPD (FR15 + FR16):** export é completo (todos os dados owner-side); delete é irreversível e hard-delete (sem soft-delete no MVP per arch §schema-design.md L121).
- **Performance:** export P95 < 1s (5 queries leves + serialização JSON; volumes MVP < 1K rows/user). Delete P95 < 2s (1 admin call + cascade DB-side).
- **Bundle (NFR4):** página pública não toca; `/dashboard/account` tem ~3 KB gz incremental (alert-dialog primitive já existente, RHF/Zod já existentes, sonner já existente). Sem nova dependência.

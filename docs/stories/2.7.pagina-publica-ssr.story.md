## Story

**As a** visitante,
**I want** acessar `/@username` e ver o avatar, nome, bio e links visíveis do usuário,
**so that** eu encontre rapidamente o que estou procurando.

## Acceptance Criteria

1. Rota `app/@[username]/page.tsx` resolve username server-side; 404 se inexistente ou `page.is_published=false`.
2. Renderização SSR (Server Component) com fetch único: profile + page + links visíveis.
3. Layout vertical mobile-first: avatar + display_name + bio + lista de links com ícones.
4. Cada link é `<a>` com `target="_blank" rel="noopener noreferrer"`.
5. Meta tags dinâmicas: title = `${display_name} (@${username}) — BioLink`; OG image placeholder.
6. Lighthouse ≥ 90 (todas as 4 categorias) na página de um perfil seed.
7. Testes de integração validam o data fetch da rota: profile encontrado → renderiza N links visíveis; profile inexistente → 404; `page.is_published=false` → 404; link com `is_visible=false` → omitido do render.

    ```ts
    const { data: pageRow } = await supabase
      .from('pages')
      .select('id, theme, is_published, profiles!inner(username, display_name, bio, avatar_url)')
      .eq('profiles.username', usernameLower)
      .eq('is_published', true)
      .maybeSingle();

      .from('links')
      .select('id, title, url, icon, position')
      .eq('page_id', pageRow.id)
      .eq('is_visible', true)
      .order('position', { ascending: true });
    ```

### Decisão DEV-1 — `app/[username]/page.tsx` (não `app/@[username]/page.tsx`)

**Problema:** Arch §Routing Architecture L1167 + §Unified Project Structure L1591 prescrevem literalmente o path `app/@[username]/page.tsx`. Porém **no Next.js 16, qualquer pasta começando com `@` é tratada como parallel route slot** (ver Next.js docs "Parallel Routes"), o que rejeita o uso como segmento de URL.

**Resolução pragmática:** usar `app/[username]/page.tsx` (segmento dinâmico simples) e validar no servidor `params.username.startsWith('@')` → senão `notFound()`. Strip do `@` antes do DB lookup. Funciona porque:

1. Rotas estáticas (`/`, `/login`, `/dashboard`, `/api/*`) **têm precedência** sobre `[username]` no resolver de rotas do Next.js.
2. `middleware.ts:42` já bypassa `path.startsWith('/@')` (Story 1.7) — anon-access intacto.
3. `lib/reserved-usernames.ts` (Story 2.1) bloqueia signups com nomes que colidem com paths estáticos.

**Divergência consciente** documentada em comentário-bloco no header de `app/[username]/page.tsx` (precedente: `middleware.ts:6-19` que documenta divergências do snippet didático do arch). @po decide no gate se quer atualizar arch §Routing L1167+L1591 (post-story) ou aceitar a divergência como nota.

**Alternativa rejeitada (postergada):** rewrite em `next.config.ts` mapeando `/@:username` → `/u/:username` interno. Mais complexo, sem ganho — a guard `startsWith('@')` é trivial e local.

### Decisão DEV-2 — Tracking server-side é Story 4.2, NÃO desta story

Arch §Workflow 2 (L714-740) sequência inclui `SSR ->> DB: INSERT page_views (server-side, hashed PII)`. Porém:

- **PRD Story 2.7 ACs (1-7) não mencionam tracking** — todas as 7 ACs são sobre render, SSR, 404, meta tags e Lighthouse.

**Decisão:** esta story é puramente de **render**. Story 4.2 estenderá `app/[username]/page.tsx` para incluir a chamada a `insertPageView()` server-side. Hoje: zero side-effects extra na primeira render → Lighthouse limpo (AC6).

### Decisão DEV-3 — Query strategy: 2 round-trips com embed vs 1 round-trip via RPC

`schema-design.md` L232-245 (AP-1) escreve o canônico em **2 SQL statements separados** (profile+page join → links by page_id). Supabase JS SDK suporta JOIN via embed (`pages.select('…, profiles!inner(…)')`), mas **não** combina os dois statements em 1 round-trip — o equivalente seria uma função RPC. Avaliações:

- **2 round-trips com embed (escolhido):** simples, zero migration nova, RLS aplica naturalmente. Latência: 2 × ~30-50ms = 60-100ms (Supabase pooler em sa-east-1). Cabe no P95 < 100ms alvo.
- **1 round-trip via RPC `get_public_page(slug)`:** exigiria nova migration `0006` + função `SECURITY INVOKER`. Mais complexo, **não recomendado para esta story** — postergar se Lighthouse mostrar gargalo de TTFB. Dev pode propor refactor pós-2.7 se medições justificarem; criar item no backlog se aplicável.

### Decisão DEV-4 — Avatar fallback quando `avatar_url` é null

Profile signup-fresh pode ter `avatar_url=null` (Story 1.5 não força upload). Fallback (Task 4.2):

- **Opção A (escolhida):** ícone `<User/>` de lucide-react dentro de `<div className="rounded-full bg-muted">` 96×96 — preserva LCP (sem `next/image` quando não há src real) e a11y (`<User aria-hidden="true">`).
- **Opção B (rejeitada):** iniciais do `display_name`/`username` em fundo color-hashed. Mais visual, mas requer color-hash util novo — overkill para MVP.

Opção A é precedente shadcn/ui Avatar (componente `Avatar` da Story 3.4 ainda não materializado — usar `<div>` + lucide até lá; refactor para `<Avatar>` em 3.4 é trivial).

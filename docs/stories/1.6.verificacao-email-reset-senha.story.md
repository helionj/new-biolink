## Story

**As a** usuário do BioLink que acabou de se cadastrar (ou esqueceu a senha),
**I want** confirmar meu email via link recebido e poder solicitar/aplicar um reset de senha,
**so that** minha conta esteja protegida contra acesso não autorizado e eu não fique trancado fora se esquecer a senha.

## Acceptance Criteria

1. **Email de verificação enviado pelo Supabase Auth após signup.** Em `biolink-dev`, `mailer_autoconfirm` é revertido para `false` via Management API (`PATCH /v1/projects/{ref}/config/auth`); a partir daí, `supabase.auth.signUp({...})` envia automaticamente o email de confirmação para o endereço cadastrado. O link no email aponta para `${NEXT_PUBLIC_SITE_URL}/auth/callback?code=...&type=signup` (URL gerada pelo template). O Route Handler `app/(auth)/auth/callback/route.ts` executa `supabase.auth.exchangeCodeForSession(code)` (PKCE flow do `@supabase/ssr`), set dos cookies HTTP-only, e em sucesso `redirect('/dashboard')`. Em falha do exchange (código expirado, já consumido, ou inválido), `redirect('/login?error=auth_callback_failed')` com toast PT-BR exibido no `/login` via `error` searchParam ("Não foi possível confirmar o link. Solicite um novo email.").

2. **Página `/reset-password`** (`app/(auth)/reset-password/page.tsx`) renderiza `<ResetPasswordRequestForm />` (Client Component) com 1 campo (email) validado client-side via **react-hook-form + zodResolver** usando `ResetPasswordRequestInput` em `lib/validators/auth.ts` (`{ email: z.string().email('Informe um email válido') }`). Submit chama Server Action `requestPasswordReset({ email })` que invoca `supabase.auth.resetPasswordForEmail(email, { redirectTo: ${NEXT_PUBLIC_SITE_URL}/auth/callback?next=/reset-password/confirm })`. **Anti-enumeration (arch §Security linha 2147):** o Server Action SEMPRE retorna `{ ok: true, data: undefined }` independentemente de o email existir ou não no banco — mensagem do toast em sucesso é genérica em PT-BR ("Se este email estiver cadastrado, você receberá um link para redefinir sua senha em alguns minutos."). Botão "Enviar" desabilitado enquanto `isSubmitting`.

3. **Página `/reset-password/confirm`** (`app/(auth)/reset-password/confirm/page.tsx`) é a página de "nova senha" — só acessível quando o usuário tem session ativa estabelecida pelo `/auth/callback` (Supabase recovery flow gera session temporária após `exchangeCodeForSession`). Page é Server Component que: (a) chama `supabase.auth.getUser()`; se `!user`, `redirect('/reset-password?error=session_expired')`; (b) renderiza `<ResetPasswordConfirmForm />` (Client Component) com 2 campos (`newPassword` ≥ 8 chars, `confirmPassword` matching) validados via `ResetPasswordConfirmInput` Zod schema (mesma regra de password do `SignUpInput`). Submit chama Server Action `confirmPasswordReset({ newPassword })` que invoca `supabase.auth.updateUser({ password: newPassword })`. Em sucesso: `redirect('/dashboard')` (session já estabelecida). Em falha (session expirou entre o GET e o POST, ou Supabase rejeitou a senha — ex: muito similar à antiga): toast PT-BR + retorno `{ ok: false, error: '...' }`.

4. **Route Handler `/auth/callback` é multi-purpose** (mesmo handler para signup confirm + password recovery + magic link futuro). Implementação:
   - Lê `code` (PKCE) + `next` (path opcional para redirect pós-exchange) + `type` (`signup` | `recovery` — opcional, vem do template do email) dos `searchParams`.
   - Se `code` ausente: `redirect('/login?error=auth_callback_failed')`.
   - `await supabase.auth.exchangeCodeForSession(code)`; se `error`: `redirect('/login?error=auth_callback_failed')`.
   - Em sucesso: `redirect(next ?? '/dashboard')`. Para o flow de recovery, o template do email gera link com `?next=/reset-password/confirm`; para o flow de signup, o template não inclui `next` → cai no `/dashboard` default.
   - `redirect` propaga via `NextResponse.redirect(new URL(target, req.url))` para preservar origin.

5. **Email templates customizados em PT-BR** via Management API (`PATCH /v1/projects/{ref}/config/auth` com `mailer_subjects_*` + `mailer_templates_*_content`) — atualizar **mínimo 2 templates**: (a) `mailer_subjects_confirmation` = "Confirme seu email no BioLink" + body PT-BR com `{{ .ConfirmationURL }}` (Story 1.6 confirm signup); (b) `mailer_subjects_recovery` = "Redefina sua senha do BioLink" + body PT-BR com `{{ .ConfirmationURL }}` (este link vem com `type=recovery` no path do callback). Documentar payload exato + comando curl em `docs/dev-setup.md §13` (substituir conteúdo da seção criada na Story 1.5; manter histórico do toggle Story 1.5 abaixo da seção principal como sub-heading "Histórico"). Outros 3 templates (magic_link, invite, email_change) ficam com strings default em inglês — refatorar quando exigidos por features futuras. **Constraint NFR17:** continua sem provider externo (resend/sendgrid); somente o built-in do Supabase Auth.

Botão chama nova Server Action `resendVerificationEmail()` que invoca `supabase.auth.resend({ type: 'signup', email: user.email })`. - [x] **Task 4 — Route Handler `/auth/callback`** (AC1, 4)
  - [x] 4.1 Criar `app/(auth)/auth/callback/route.ts`:

    ```typescript
    import { NextResponse, type NextRequest } from 'next/server';
    import { createClient } from '@/lib/supabase/server';

    export async function GET(req: NextRequest) {
      const { searchParams, origin } = req.nextUrl;
      const code = searchParams.get('code');
      const next = searchParams.get('next') ?? '/dashboard';

      if (!code) {
        return NextResponse.redirect(new URL('/login?error=auth_callback_failed', origin));
      }

      const supabase = await createClient();
      const { error } = await supabase.auth.exchangeCodeForSession(code);
      if (error) {
        console.error('[auth/callback] exchange failed:', error.message);
        return NextResponse.redirect(new URL('/login?error=auth_callback_failed', origin));
      }

      // next pode vir como path relativo (ex: '/reset-password/confirm') ou ausente.
      // Validar que é path relativo (defesa contra open redirect) — rejeitar absolute URLs.
      const safeNext = next.startsWith('/') && !next.startsWith('//') ? next : '/dashboard';
      return NextResponse.redirect(new URL(safeNext, origin));
    }
    ```

**Pattern canônico (idêntico Story 1.5):**

```typescript
'use server';

import { redirect } from 'next/navigation';
import { z } from 'zod';
import type { ActionResult } from '@/lib/result';
import { createClient } from '@/lib/supabase/server';
import { env } from '@/lib/env';
import { ResetPasswordRequestInput, ResetPasswordConfirmInput } from '@/lib/validators/auth';

export async function requestPasswordReset(raw: unknown): Promise<ActionResult<void>> {
  const parsed = ResetPasswordRequestInput.safeParse(raw);
  if (!parsed.success) {
    return {
      ok: false,
      error: 'Entrada inválida',
      fieldErrors: flattenFieldErrors(parsed.error), // helper já existe Story 1.5
    };
  }

  const supabase = await createClient();
  const { error } = await supabase.auth.resetPasswordForEmail(parsed.data.email, {
    redirectTo: `${env.NEXT_PUBLIC_SITE_URL}/auth/callback?next=/reset-password/confirm`,
  });

  // Anti-enumeration: sempre sucesso ao client (NFR + arch §Security linha 2147)
  if (error) console.error('[requestPasswordReset] supabase error:', error.message);
  return { ok: true, data: undefined };
}
```

### Route Handler `/auth/callback` — implementação canônica

[Source: documentação oficial Supabase Auth Helpers para Next.js 16 + `@supabase/ssr` v0.10+ — PKCE flow. Referência cruzada interna: arch §Auth Flow linha 1550-1553 "FE→FE: redirect /reset-password/confirm"]

```typescript
// app/(auth)/auth/callback/route.ts
import { NextResponse, type NextRequest } from 'next/server';
import { createClient } from '@/lib/supabase/server';

export async function GET(req: NextRequest) {
  const { searchParams, origin } = req.nextUrl;
  const code = searchParams.get('code');
  const next = searchParams.get('next') ?? '/dashboard';

  if (!code) {
    return NextResponse.redirect(new URL('/login?error=auth_callback_failed', origin));
  }

  const supabase = await createClient();
  const { error } = await supabase.auth.exchangeCodeForSession(code);
  if (error) {
    console.error('[auth/callback] exchange failed:', error.message);
    return NextResponse.redirect(new URL('/login?error=auth_callback_failed', origin));
  }

  // Defesa contra open redirect: aceitar apenas path relativo começando com '/'
  // mas não '//' (protocol-relative URL evitada).
  const safeNext = next.startsWith('/') && !next.startsWith('//') ? next : '/dashboard';
  return NextResponse.redirect(new URL(safeNext, origin));
}
```

**Pontos-chave:**

- `exchangeCodeForSession(code)` é o método PKCE do `@supabase/ssr`. Set dos cookies HTTP-only acontece via `setAll` do cookie adapter de `lib/supabase/server.ts` (mesmo pattern usado em Server Actions).
- `origin` vem de `req.nextUrl.origin` — automaticamente `http://localhost:3000` em dev ou URL Vercel em deploy. NÃO usar `env.NEXT_PUBLIC_SITE_URL` aqui (este apenas para `redirectTo` ao Supabase Auth).
- `console.error` é o mecanismo de logging disponível (Vercel Logs captura per arch §Tech Stack linha 188). Sem Sentry no MVP.

### Middleware — escopo expandido

[Source: middleware.ts atual linhas 6-7 + docs/architecture.md §Routing > Protected Route Pattern linhas 1183-1184]

**Mudança mínima nesta story** (Story 1.7 fará o redesign completo):

```typescript
// middleware.ts (atual — Story 1.5):
const PROTECTED_PATHS = ['/dashboard'];
const AUTH_PAGES = ['/login', '/signup'];

// middleware.ts (Story 1.6):
const PROTECTED_PATHS = ['/dashboard'];
const AUTH_PAGES = ['/login', '/signup', '/reset-password'];
// IMPORTANTE: '/reset-password' NÃO '/reset-password/confirm'.
// /reset-password/confirm precisa de session válida (estabelecida pelo callback) —
// é uma "auth completion page", não uma auth landing page. Middleware NÃO redireciona
// para /dashboard quando user tem session em /reset-password/confirm porque o matcher
// só captura prefix '/reset-password' que NÃO faz `path.startsWith('/reset-password/confirm')`
// retornar true para o startsWith de '/reset-password' — atenção: ele RETORNA true.
// Para evitar isso, usar comparação exata em AUTH_PAGES OU mudar o array para incluir
// somente '/reset-password' E usar `path === p || (path.startsWith(p + '/') && p !== '/reset-password')` lógica.
```

**Decisão pragmática:** dado o caveat acima, usar comparação **exata** em vez de `startsWith` para `/reset-password` (já que sub-paths como `/confirm` querem comportamento oposto):

```typescript
// middleware.ts (Story 1.6 — refactor mínimo):
const PROTECTED_PATHS = ['/dashboard'];
// Exatos: redireciona usuário logado de volta ao /dashboard se tentar acessá-las.
// O matcher do config já restringe quais URLs invocam o middleware.
const AUTH_PAGES_EXACT = ['/login', '/signup', '/reset-password'];

// ...
if (AUTH_PAGES_EXACT.includes(path) && user) {
  return redirectWithCookies('/dashboard');
}
```

**E atualizar `config.matcher`** para incluir `/reset-password` e `/reset-password/confirm` e `/auth/callback`:

```typescript
export const config = {
  matcher: [
    '/signup',
    '/login',
    '/reset-password',
    '/reset-password/confirm',
    '/dashboard',
    '/dashboard/:path*',
    '/auth/callback',
  ],
};
```

**Por que incluir `/auth/callback` no matcher:** o Route Handler `/auth/callback` precisa do middleware NÃO interceptá-lo com lógica de auth-pages (ele está sempre acessível, autenticado ou não) — ao mesmo tempo, queremos que o cookie refresh do middleware aconteça no path (refresh de session pode acontecer no GET do callback antes do `exchangeCodeForSession`). Solução: incluir `/auth/callback` no matcher MAS NÃO no `AUTH_PAGES_EXACT` nem em `PROTECTED_PATHS` — o middleware roda, refresca cookies se necessário, e cai no `return supabaseResponse` neutro. (Comportamento default desejado.)

### Technical Constraints

- **Next.js 16 + React 19:** Route Handlers (`route.ts`) usam `NextRequest`/`NextResponse` para redirect. `redirect()` de `next/navigation` é para Server Components/Actions; **NÃO** chamar `redirect()` dentro de Route Handler — usar `NextResponse.redirect(new URL(...))`.
- **@supabase/ssr 0.10+:** `exchangeCodeForSession` é PKCE flow. NÃO usar `signInWithIdToken` ou outras variantes. Cookies refresh acontece automaticamente via `setAll` do server client (já configurado em `lib/supabase/server.ts`).
- **Site URL + Redirect URLs allowlist (Supabase):** Dashboard → Auth → URL Configuration. `Site URL` deve apontar para `NEXT_PUBLIC_SITE_URL`. `Redirect URLs` deve listar pelo menos `${SITE_URL}/auth/callback` (mais `*.vercel.app/auth/callback` para previews). Sem isso, `resetPasswordForEmail` recusa o `redirectTo` por segurança.
- **Open redirect protection:** Route Handler `/auth/callback` valida `next` searchParam aceitando apenas paths relativos (`/...` mas NÃO `//...`). Sem essa validação, atacante pode criar email com `?next=https://evil.com` e redirecionar usuários autenticados.
- **Strict TypeScript:** `noUncheckedIndexedAccess` ativo — atenção em `searchParams.get(...)` que retorna `string | null`.
- **i18n PT-BR (arch §Coding Standards linha 2402):** literais inline. Aceitar duplicação eventual.
- **Server-First (arch §Coding Standards linha 2390):** páginas `/reset-password` e `/reset-password/confirm` são Server Components; forms (ResetPasswordRequestForm, ResetPasswordConfirmForm, ResendEmailButton) são `'use client'`.
- **Service-role isolation (arch §Coding Standards linha 2395):** `lib/supabase/admin.ts` permanece apenas em integration tests para cleanup/validação. Esta story NÃO consome admin em prod path — todas as Server Actions usam o anon path com session cookies (RLS aware) ou o Management API HTTP direto via curl (Task 2 e config).

### Project Structure Notes

Discrepâncias / decisões tomadas durante o draft:

1. **Path canônico do callback: `app/(auth)/auth/callback/route.ts` (route group `(auth)`)**, não `app/auth/callback/route.ts` na raiz. Justificativa: arch §Routing Architecture > Route Organization linha 1159 lista explicitamente `auth/callback/route.ts` DENTRO do grupo `(auth)`. O grupo `()` é sintaxe Next.js para "agrupar sem afetar URL" — o URL resultante é `/auth/callback`. Coding Standards arch linha 2418 menciona `app/auth/callback/**` como path autorizado para `admin` import, mas isso é só uma regra ESLint que cobre ambos formatos via path matcher. **Decisão:** usar `app/(auth)/auth/callback/route.ts` por consistência com o resto do grupo `(auth)/`. Se o ESLint complain do path admin, ajustar a regra em Story 1.7.

2. **`signUp` Server Action comportamento mudou:** com `mailer_autoconfirm: false`, `supabase.auth.signUp` retorna `{ user, session: null }`. O `redirect('/dashboard')` atual cairia em loop (middleware vê `!user` → redirect `/login`). **Decisão final (Task 3.5):** retornar `{ ok: true, data: undefined }` SEM redirect server-side; o form do signup faz `router.push('/login?message=verify_email')` client-side, exibindo toast PT-BR "Conta criada! Confirme seu email para fazer login." Alternativa rejeitada: criar `/signup/verify-email-sent` placeholder dedicada (acrescenta 1 página por benefício marginal — toast é suficiente).

3. **Middleware: `AUTH_PAGES` exact match em vez de `startsWith`.** Necessário porque `/reset-password/confirm` precisa de session válida (oposto do comportamento "logado → /dashboard"). Solução: mudar matching para `includes(path)` (igualdade exata) em `AUTH_PAGES_EXACT` (ver Dev Notes §Middleware). Story 1.7 fará a refatoração completa do middleware com regex patterns mais sofisticados.

4. **`resendVerificationEmail` não está no inventário canônico (arch §API Spec linhas 416-423)**, mas é necessária para satisfazer PRD AC4 ("banner persiste até verificação concluída") em UX-friendly (sem reenvio, usuário fica sem opção se email se perdeu). **Decisão:** adicionar à `server/auth/actions.ts` mesmo sem listing explícito. Justificativa enquadrada em arch §Authorization linha 1567-1568 (Supabase Auth wrappers) — é uma extensão natural do pattern. Documentar como adição da Story 1.6 no Change Log.

5. **`NEXT_PUBLIC_SITE_URL` é nova env var** (não listada em arch §Tech Stack nem em `.env.example` original). Necessária para construir `redirectTo` absoluto em `resetPasswordForEmail` (Supabase Auth rejeita relative URLs). Cross-ref Story 1.3 (CI/CD secrets pipeline) — owner aplica em GH Secrets + Vercel manualmente (Task 1.5 é handoff a @devops, não bloqueia Done desta story).

6. **Test integration `signUp` reescrita** quebra paridade com a story 1.5 que assumia `mailer_autoconfirm: true`. Documentado em `docs/dev-setup.md §13` (Story 1.5) que "Story 1.6 atualiza essa suíte para usar `/auth/callback` flow". **Decisão:** REESCREVER o cenário existente em vez de adicionar variant novo — caso contrário teríamos dois testes mutuamente exclusivos no mesmo arquivo (um assumindo autoconfirm=true, outro =false). A versão definitiva é a desta story.

7. **Smoke manual end-to-end NÃO automatizado** (Task 7). Justificativa: integration tests automatizados não conseguem verificar o conteúdo de emails reais nem clicar em links — exigiria stub do mailer ou Playwright + mailinator API. NFR/arch declara sem E2E no MVP (arch §Testing Pyramid linha 2222). **Trade-off explícito:** owner roda smoke manual antes do PR merge; cobertura automatizada cobre os Server Actions diretamente.

8. **Email templates HTML mínimo (Task 2.1).** Sem CSS inline complexo, sem imagens, sem layout responsivo. Justificativa: emails do BioLink são transacionais simples (clique no link) — qualidade visual fica para Phase 2 (revisitar com @ux-design-expert se branding mudar). Render correto em gmail/apple-mail/outlook web é o gate funcional.

9. **Cross-story coupling com 1.7 (Middleware completo):** esta story expande `middleware.ts` minimamente (adiciona `/reset-password` ao AUTH_PAGES com lógica de exact match) — Story 1.7 fará o redesign completo cobrindo todas as rotas privadas + edge cases (refresh proativo, session expirada graceful, etc.). Cross-ref documentado inline no `middleware.ts` (já presente da 1.5).

10. **Branch protection rule não muda:** 9 required checks já estabelecidos em Story 1.4/1.5. Esta story não adiciona nem remove jobs no `.github/workflows/ci.yml` — apenas adiciona testes ao job `test-integration` existente. **Caveat:** `pnpm build` no CI vai falhar se `NEXT_PUBLIC_SITE_URL` não estiver em GH Secrets/Vars (porque `env.ts` faz parse com Zod em compile-time). Task 1.5 é handoff a @devops para garantir isso antes do PR ser aberto.

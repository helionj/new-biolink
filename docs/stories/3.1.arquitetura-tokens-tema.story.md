## Story

**As a** desenvolvedor,
**I want** um sistema de tokens baseado em CSS variables que suporte troca de tema em runtime,
**so that** os 3 presets (e temas futuros) reusem o mesmo código de componentes.

## Acceptance Criteria

1. `app/globals.css` define tokens (cor, spacing, radius, font) via CSS variables sob seletores `[data-theme="light"]`, `[data-theme="dark"]`, `[data-theme="brand"]`.
2. Tema aplicado em `<html data-theme="...">` via Server Component (sem flash de tema).
3. Helper `lib/theme.ts` com tipo `Theme = 'light' | 'dark' | 'brand'`.
4. Storybook-like page em `/dev/themes` (apenas em dev) demonstra todos os tokens.

- [x] **Task 2 — Criar helper `lib/theme.ts`** (AC: 3)
  - [x] 2.1 Criar `lib/theme.ts` (arquivo novo — `find lib -name "theme*"` confirma ausência; arch §Unified Project Structure L1624 prescreve o path). Estrutura:

    ```ts
    // lib/theme.ts
    import type { Database } from '@/lib/supabase/types';

    /**
     * Theme preset literal — alinhado ao enum `theme_preset` do schema
     * (`0002_profiles.sql`, `0003_pages.sql`). Fonte única de verdade: o DB.
     * Importar de `@/lib/theme` em qualquer Server Component/Action que precise
     * tipar `data-theme` ou comparar contra paleta.
     */
    export type Theme = Database['public']['Enums']['theme_preset'];

    /** Conjunto runtime para validações (zod / lookups). */
    export const THEMES = ['light', 'dark', 'brand'] as const;

    /** Default aplicado quando nenhum tema explícito está disponível (anon, sem page.theme). */
    export const DEFAULT_THEME: Theme = 'light';

    /**
     * Type-guard para validar input externo (cookie, URL param, page.theme).
     * Use sempre que receber um string vindo de fora do TS strict.
     */
    export function isTheme(value: unknown): value is Theme {
      return typeof value === 'string' && (THEMES as readonly string[]).includes(value);
    }

    /**
     * Normaliza qualquer input para um Theme válido; fallback para DEFAULT_THEME.
     * Use em layouts/SSR que recebem theme via param/cookie sem garantia de shape.
     */
    export function resolveTheme(value: unknown): Theme {
      return isTheme(value) ? value : DEFAULT_THEME;
    }
    ```

### Decisão DEV-1 — Reconciliação `.dark` ↔ `[data-theme="dark"]` via seletor composto

**Problema:** O globals.css (linha 70) sinaliza: `/* shadcn dark mode class — coexiste com [data-theme='dark']; Story 3.1+ reconcilia */`. Coexistir hoje funciona via duplicação de valores (lines 53-59 + 71-91 contêm os mesmos tokens de cor). Manter duplicação é dívida técnica e risco de drift na Story 3.2 (paletas reais).

**Resolução:** seletor composto `[data-theme="dark"], .dark { … }` em um único bloco. Razão:

1. **shadcn primitives copiados em Story 1.5** (`button.tsx`, `input.tsx`, `card.tsx`, `dialog.tsx`, `dropdown-menu.tsx`, etc.) podem usar o Tailwind `dark:` variant internamente — esse variant é alimentado por `@custom-variant dark (&:is(.dark *))` em `app/globals.css:4`, que **depende da classe `.dark`** estar em algum ancestral. Remover `.dark` quebra os componentes.
2. **`<html data-theme="dark">` sozinho não aciona o `dark:` variant** porque o `@custom-variant` está hardcoded em `.dark`. Para reconciliar sem reescrever o variant, o caminho mais barato é fazer ambos os seletores aplicarem os mesmos tokens.
3. **Refactor futuro** (Story 3.x ou tech-debt): redefinir `@custom-variant dark (&:is([data-theme="dark"] *))` — isso eliminaria `.dark` completamente. Hoje, **fora de escopo** (toca todos os primitives shadcn; risk/value desfavorável para a Story 3.1).

**Alternativa rejeitada:** definir `[data-theme="dark"]` E `.dark` em blocos separados com `@apply` cruzado. Mais complexo, sem ganho, e o `@apply` entre seletores não é suportado pelo Tailwind 4 da forma esperada (CSS-first vs JS-first config).

### Decisão DEV-2 — Spacing tokens: honrar Story 1.8 v0.2 (sem custom `--spacing-*`)

**Problema:** AC1 lista "cor, spacing, radius, font" como tokens a definir sob seletores `[data-theme=...]`. Story 1.8 (Change Log v0.2, documentado em globals.css L93-99) explicitamente **rejeitou** custom `--spacing-*` tokens: "AC2 'spacing' usa a escala default do Tailwind 4. Nenhum doc-fonte (PRD/arch) especifica tokens --spacing-\* custom — inventá-los violaria Constitution Art. IV (No Invention)."

**Resolução:** Interpretar AC1 "spacing" como **vocabulário de design tokens já em escopo via Tailwind 4 default** (`p-4`, `gap-6`, etc. — todos derivados da escala `0.25rem * n` interna do Tailwind 4, expostos automaticamente quando se usa `@import 'tailwindcss';` em L1). Sem var custom `--space-*` por theme. Razão adicional: temas **não variam spacing** — variam cor (sempre), radius (raramente), font (raramente). A FR12 e o brief mencionam apenas paletas; spacing per-theme seria invenção fora dos doc-fontes.

**Consequência:** Se @po em validation considerar AC1 não satisfeito sem `--space-*` explícito, opções:

1. Adicionar `--space-section: 1.5rem; --space-card: 1rem;` em `:root, [data-theme="light"]` (e idênticos em `dark`/`brand` se não variam) — **mínima invenção**, só para honrar AC literal.
2. Expandir Story 1.8 com um amendment retroativo formal documentando que spacing tokens não existem por design.

Recomendação @sm: **opção (1)** se @po pedir, **opção (2)** se @po concordar com a interpretação atual. **Linha base desta draft é a interpretação atual** (sem custom spacing tokens).

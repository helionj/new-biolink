## Story

**As a** desenvolvedor do BioLink,
**I want** um middleware centralizado redirecionando guests de rotas privadas (`/dashboard/*`) e usuários autenticados de rotas de auth (`/login`, `/signup`, `/reset-password`), preservando exceções públicas (`/`, `/@<username>`, `/api/track/*`, assets) e refresh transparente de sessão,
**so that** a proteção de rotas seja consistente, testável e o pattern canônico do `@supabase/ssr` (refresh de cookies via `setAll` propagado em redirects) fique enforçado em um único ponto da árvore.

## Acceptance Criteria

1. **Matcher amplo cobrindo todas as rotas exceto assets estáticos.** O `config.matcher` em `middleware.ts` é refatorado para o padrão canônico de `docs/architecture.md §Routing Architecture > Protected Route Pattern` (linha 1227): `'/((?!_next/static|_next/image|favicon.ico|.*\\.(?:svg|png|jpg|jpeg|gif|webp)$).*)'`. O matcher passa a interceptar TODAS as rotas exceto: (a) arquivos estáticos de `_next/static`/`_next/image`; (b) `favicon.ico`; (c) qualquer arquivo com extensão de imagem (`.svg`/`.png`/`.jpg`/`.jpeg`/`.gif`/`.webp`). Substitui a lista enumerada atual (`['/signup', '/login', '/reset-password', '/reset-password/confirm', '/auth/callback', '/dashboard', '/dashboard/:path*']` — `middleware.ts:84-92`) — não há mais "esquecer de incluir uma rota": o default passa a ser **interceptar**, e o bypass é explicit em código.

2. **Rotas protegidas (`/dashboard/*`) exigem sessão Supabase válida.** `PROTECTED_PREFIXES = ['/dashboard']`. Em request a path que `startsWith('/dashboard')`, o middleware chama `supabase.auth.getUser()`; se `!user`, monta redirect para `/login?next=<path>` preservando o pathname original (sem search params do request, apenas o pathname) — `next` permite ao `/login` redirecionar o usuário pós-autenticação para o destino pretendido (consumo de `next` no `signIn` pós-AC2 é fora de escopo desta story — apenas plumbing do query param). Redirect propaga cookies refreshed do `supabaseResponse` para preservar sessão pendente (helper `redirectWithCookies` da 1.6 mantido).

3. **Rotas de auth (`/login`, `/signup`, `/reset-password`) redirecionam para `/dashboard` se sessão existe.** `AUTH_PAGES_EXACT = ['/login', '/signup', '/reset-password']` — matching exato (igualdade estrita), idêntico ao pattern da 1.6 para não engolir `/reset-password/confirm` (este path tem semântica oposta — exige session ativa do recovery flow para renderizar). Em request a path == elemento de `AUTH_PAGES_EXACT` com `user` presente, redirect para `/dashboard` com cookies propagados. `/reset-password/confirm` cai no branch neutro (não é AUTH_PAGES_EXACT nem PROTECTED — o auth-guard server-side da página já cobre o gate de session).

4. **Rotas públicas bypassam o middleware de auth.** Bypass early-return (antes de qualquer chamada a `supabase.auth.getUser()`) para:
   - `/@<username>` — qualquer path que `req.nextUrl.pathname.startsWith('/@')` (Story 2.7 implementará `/@[username]/page.tsx`; bypass já estabelecido aqui evita refactor futuro).
   - `/api/track/*` — qualquer path que `startsWith('/api/track')` (Story 4.X implementará `/api/track/click` e `/api/track/view`; tracking anônimo público, sem auth — arch §Routing linha 1191).
   - `/auth/callback` — Route Handler de PKCE da 1.6; middleware NÃO o redireciona, mas continua executando o pipeline de cookie refresh (`getUser()` no callback handler dispara `exchangeCodeForSession` e setta os cookies de session — middleware roda antes para refresh do session anterior se houver).
   - `/` — landing pública (Story 1.9 implementará `app/page.tsx` com CTA SEO; pode haver `user` autenticado, mas o middleware NÃO redireciona automaticamente — o componente da landing trata o estado autenticado client-side via toggle CTA "Ir para meu dashboard" per PRD Story 1.9 AC2).

   Estas rotas caem no `return supabaseResponse` neutro (com cookies refreshed se aplicável).

5. **Refresh transparente de sessão via pattern oficial `@supabase/ssr`.** O middleware mantém o pattern canônico de Stories 1.5/1.6: `let supabaseResponse = NextResponse.next({ request: req })`, `createServerClient` com adapter `cookies: { getAll, setAll }` onde `setAll` (a) propaga novos cookies via `req.cookies.set` para que requests downstream (Server Components, Server Actions) vejam a session refreshed E (b) reconstrói `supabaseResponse = NextResponse.next({ request: req })` com `supabaseResponse.cookies.set` para que o browser receba os cookies no response. Qualquer redirect dentro do middleware copia `supabaseResponse.cookies.getAll()` para o `NextResponse.redirect()` retornado — sem isso o browser perde a sessão entre redirects (já tratado pelo helper `redirectWithCookies` da 1.6, preservado). **Esta AC é não-testável diretamente em integration test** (refresh real depende de expiração de token Supabase) — verificada via inspeção de código + smoke manual de longa duração (opcional, não bloqueante per arch §Testing Pyramid linha 2222).

6. **Suite de integration tests dedicada (`tests/integration/middleware.test.ts`)** cobre a matriz `auth × path` com pelo menos os 10 cenários abaixo. Pattern: importa a função `middleware` exportada de `middleware.ts` (não passa pelo Next.js runtime; testa a função pura), mocka `@supabase/ssr.createServerClient` para retornar `{ auth: { getUser: () => ({ data: { user: null | { id, email } } }) } }` controlável, e constrói um `NextRequest` minimal via construtor padrão. Cenários obrigatórios:
   - **Guest em `/dashboard`** → redirect para `/login?next=/dashboard` (response.status === 307, location header set).
   - **Guest em `/dashboard/profile`** → redirect para `/login?next=/dashboard/profile`.
   - **Authenticated em `/dashboard`** → passthrough (response sem `Location`, status 200/equivalente via `NextResponse.next`).
   - **Guest em `/login`** → passthrough.
   - **Authenticated em `/login`** → redirect para `/dashboard`.
   - **Authenticated em `/signup`** → redirect para `/dashboard`.
   - **Authenticated em `/reset-password`** → redirect para `/dashboard`.
   - **Authenticated em `/reset-password/confirm`** → passthrough (não é auth page para esse pattern; guard server-side da página é separado).
   - **Authenticated em `/@helion`** → passthrough (bypass via `/@` prefix; `getUser` nem é chamado).
   - **Guest em `/@helion`** → passthrough (bypass; público sempre).
   - **Authenticated em `/auth/callback?code=xxx`** → passthrough (bypass; o Route Handler executa o exchange).
   - **Authenticated em `/api/track/click`** → passthrough (bypass).
   - **Guest em `/`** → passthrough (landing pública; AC4 sub-bullet 4).

   Asserções específicas: response.headers.get('Location') vs. response inexistir; cookies refreshed (mock retorna `setAll` invocado quando aplicável) — apenas smoke do path. **Não testar refresh real de token** (AC5).

### Architecture — Source of Truth

[Source: docs/architecture.md §Routing Architecture > Protected Route Pattern, linhas 1176-1229]

**Pattern canônico publicado no arch (referência direta — implementar IDENTICAMENTE ao snippet, com adaptações de `env` vs `process.env` para conformar arch §Coding Standards linha 2396 "Env via Zod"):**

```typescript
// docs/architecture.md linhas 1180-1229 (literal)
import { type NextRequest, NextResponse } from 'next/server';
import { createServerClient } from '@supabase/ssr';

const PROTECTED_PREFIXES = ['/dashboard'];
const AUTH_PAGES = ['/login', '/signup', '/reset-password'];

export async function middleware(req: NextRequest) {
  const res = NextResponse.next();

  // Páginas públicas não precisam de session check
  if (req.nextUrl.pathname.startsWith('/@')) return res;
  if (req.nextUrl.pathname.startsWith('/api/track')) return res;

  const supabase = createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
    {
      cookies: {
        getAll: () => req.cookies.getAll(),
        setAll: (toSet) =>
          toSet.forEach(({ name, value, options }) => res.cookies.set(name, value, options)),
      },
    },
  );

  const {
    data: { user },
  } = await supabase.auth.getUser();
  const path = req.nextUrl.pathname;

  if (PROTECTED_PREFIXES.some((p) => path.startsWith(p)) && !user) {
    const url = req.nextUrl.clone();
    url.pathname = '/login';
    url.searchParams.set('next', path);
    return NextResponse.redirect(url);
  }

  if (AUTH_PAGES.some((p) => path.startsWith(p)) && user) {
    const url = req.nextUrl.clone();
    url.pathname = '/dashboard';
    return NextResponse.redirect(url);
  }

  return res;
}

export const config = {
  matcher: ['/((?!_next/static|_next/image|favicon.ico|.*\\.(?:svg|png|jpg|jpeg|gif|webp)$).*)'],
};
```

**Adaptações desta story relativas ao snippet arch (justificadas):**

1. **`process.env.*!` → `env.NEXT_PUBLIC_*`:** arch §Coding Standards linha 2396 ("Env via Zod: **nunca** `process.env.X` direto fora de `lib/env.ts`") — Stories 1.5/1.6 já consomem `env` de `@/lib/env`. Manter consistência.
2. **`AUTH_PAGES.some(startsWith)` → `AUTH_PAGES.includes(path)` (exact match):** **divergência consciente** do snippet do arch — `startsWith` quebraria `/reset-password/confirm` (engoliria para `/dashboard` redirect, perdendo a página de nova senha). Story 1.6 PSN #3 documenta a decisão. O comportamento documentado no arch §Auth Flow linha 1551 ("FE→FE: redirect /reset-password/confirm" após callback) só funciona com exact match. **Esta divergência é o pattern correto** — o snippet do arch é um modelo simplificado pré-Story 1.6.
3. **Bypass `/` e `/auth/callback`:** snippet arch não os menciona — `/` cai no `return res` neutro por não ser PROTECTED nem AUTH_PAGES, mas executa `getUser()` desnecessariamente; bypass explícito é otimização + clareza. `/auth/callback` ver Project Structure Notes #1.
4. **Helper `redirectWithCookies` (Story 1.6) preservado:** snippet arch faz `NextResponse.redirect(url)` direto sem propagar cookies — bug latente (browser perde session entre redirect se Supabase tinha refreshed). Manter o helper da 1.6.

### Security Considerations

[Source: docs/architecture.md §Security Requirements > Authentication Security, linhas 2142-2148]

- ✅ **Token Storage:** cookies HTTP-only + Secure + SameSite=Lax — pattern do `@supabase/ssr` aplicado via adapter já consolidado. Esta story preserva.
- ✅ **Session Management:** refresh automático via middleware — AC5 deste documento + arch linha 2145 ("refresh automático via middleware; expiração padrão Supabase (1 hora access, 30 dias refreshs)"). Esta story preserva via pattern oficial.
- ⚠️ **`next` query param em redirect (AC2):** preservamos apenas o `pathname` original (sem search params do request). Justificativa: `next` deve ser usado APENAS para redirect pós-auth (Story 1.5/futura). Search params arbitrários do request original poderiam ser usados para exfiltrar dados sensíveis em logs — mantemos minimalismo.
- ⚠️ **Open redirect via `next`:** quando o `signIn` Server Action consumir o `next` query param (escopo de uma story futura — não desta), DEVE validar `next.startsWith('/') && !next.startsWith('//')` antes de redirect — pattern idêntico ao `safeNext` do `/auth/callback` Route Handler (Story 1.6 `app/(auth)/auth/callback/route.ts:36`). **Não escopo desta story** — apenas documentar como handoff.
- ✅ **Service-role isolation:** middleware NÃO usa `admin` client (apenas `createServerClient` com anon key). Conforme arch §Coding Standards linha 2395 — `lib/supabase/admin.ts` só em `server/`, `app/api/`, `app/auth/callback/`. ESLint rule já enforça.

### Test Strategy — integration tests dedicados

[Source: docs/architecture.md §Testing Pyramid linhas 2204-2222 + §Test Organization linhas 2224-2278]

**Decisão arquitetural Story 1.6 §Testing (deferida explicitamente para 1.7): "Não testar middleware isoladamente (Story 1.7 fará suíte dedicada)."** Esta story entrega.

**Arquivo:** `tests/integration/middleware.test.ts` (novo).

**Posicionamento na pirâmide:** middleware é "integration" — testa o handler completo (com mock de @supabase/ssr) em um único `import { middleware }` puro, sem rodar via Next runtime, sem rede, sem DB. Tradeoff: não cobrimos o glue real do Next.js Edge runtime (em produção o matcher do `config` filtra antes do handler — aqui chamamos o handler diretamente; rotas excluídas pelo matcher do `config` não rodam no Edge mas rodam nos testes se invocadas). Mitigação: testes pegam o comportamento da **função middleware**, e o build/typecheck pega o **matcher pattern** (Next 16 valida em build-time). Cobertura combinada é suficiente.

**Por que não testar via Next.js runtime real:** sem stack E2E (arch §Testing linha 2222) e sem Edge runtime adapter para Vitest no MVP — over-engineering para o ROI esperado. O pattern de "import direto + mock supabase" é o estado da arte para middleware test em projetos sem Playwright.

**Fixtures:** não precisam de Supabase real — testes são puros via mock. Sem cleanup de DB. Sem usuários `cifx-*` criados (a diferença vs auth.test.ts da 1.5/1.6).

**Coverage attribution:** arch NFR6 (backend ≥ 70%) — middleware count como backend. Esta suite adiciona ~10 cenários cobrindo 100% das branches do handler (PROTECTED, AUTH_PAGES, bypass de `/`, `/@`, `/api/track`, `/auth/callback`, branch neutro `/reset-password/confirm`).

### Project Structure Notes

1. **`/auth/callback` movido do matcher para a bypass list (mudança vs Story 1.6).** Story 1.6 deixou `/auth/callback` no matcher com comentário "para que o middleware refresque cookies se necessário antes do GET do Route Handler". Em retrospect, com o matcher amplo desta story (1.7 AC1), `/auth/callback` cairia no pipeline `getUser()` antes do handler chamar `exchangeCodeForSession`. Em um cenário onde o usuário CHEGA na `/auth/callback` com um session-cookie ainda válido de uma session antiga (ex: clicou no link de email enquanto já estava logado em outra aba), o middleware `getUser` poderia refresh cookies em paralelo ao `exchangeCodeForSession` do handler, criando uma race condition entre dois `setAll`. **Decisão:** bypass explícito de `/auth/callback`. O handler já faz seu próprio `createClient` + `exchangeCodeForSession` (que internamente faz setAll dos novos cookies de session). Trade-off: perdemos a oportunidade de refresh em URLs que terminem em `/auth/callback` sem `code` (que retornam erro) — mas o impacto é nulo (esses redirects vão para `/login?error=...` que é AUTH_PAGES; um refresh nessa rota seria irrelevante).

2. **Não usar `process.env.*!` (snippet arch linha 1194-1195) — usar `env` de `@/lib/env`.** Arch §Coding Standards linha 2396 é categórica: "**nunca** `process.env.X` direto fora de `lib/env.ts`". O snippet do arch §Routing é didático; nosso `middleware.ts` atual já consome `env` corretamente — preservar.

3. **`AUTH_PAGES` (exact match) é divergência consciente do snippet arch.** Documentada em Story 1.6 PSN #3 e re-documentada aqui em Dev Notes §Architecture > Adaptações #2. Caso o arch seja atualizado em uma story futura (ex: review do arch document por @architect), reconciliar — mas a behavior atual é o pattern correto pós-1.6.

4. **Renomear `AUTH_PAGES_EXACT` → `AUTH_PAGES`** mantém o pattern do arch (linha 1184) por nomenclatura, com comentário inline esclarecendo o exact-match. Reduz "shouting" no nome para legibilidade.

5. **`PROTECTED_PATHS` → `PROTECTED_PREFIXES`** alinhamento idêntico com arch linha 1183. Nomenclatura + semântica (prefix match via `startsWith`).

6. **Tests via import direto, não via Next Edge runtime.** Story 2.X (não esta) pode considerar usar `next-test-edge` ou similar quando estabilidade da tooling justificar. Por hora, pattern "import + mock" é o ROI correto.

7. **Sem mudança em `core-config.yaml` esperada.** Esta story é code-only. Se a Story 1.6 deixou alguma referência cross-file específica a middleware (ex: em `docs/dev-setup.md` ou `docs/qa/known-issues.md`), revisar mas não atualizar proativamente.

8. **`/reset-password/confirm` branch neutro.** Não é PROTECTED (lógica de redirect-on-not-authenticated é da page server-side per Story 1.6 ResetPasswordConfirmPage), não é AUTH_PAGES (redirect-on-authenticated é justamente o oposto do que precisamos aqui). Resultado: cai no `return supabaseResponse` neutro com cookies refreshed se aplicável. Comportamento correto.

9. **Refresh proativo de session NÃO implementado nesta story.** O pattern `@supabase/ssr` já refresca lazily (no próximo `getUser()` quando o token estiver próximo de expirar — Supabase SDK trata internamente). "Refresh proativo" no sentido de pre-refresh quando token está em janela X de expirar é otimização não-priorizada no MVP. **Fora de escopo** — Story 1.6 PSN #9 listou como ambicioso; esta story confirma deferimento.

10. **Não implementar consumo de `next` query param no `signIn`.** PRD Story 1.5 AC + Story 1.7 AC2 só requerem que o middleware **emita** o `next=<path>` no redirect para `/login`. Consumir esse query param em `signIn` (redirect pós-auth para `next` em vez de `/dashboard` hardcoded) é UX gain mas não-bloqueante. Documentado em Security Considerations acima como handoff (com warning de open-redirect validation). Pode virar 1 ticket separado ou parte de uma story futura.

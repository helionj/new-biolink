## Story

**As a** desenvolvedor,
**I want** uma tabela `profiles` com RLS policies estritas, trigger de bootstrap automático e cenários de seed testados,
**so that** as futuras tabelas user-data (pages, links, click_events, page_views) sigam um padrão de segurança validado em CI e o signup já produza um perfil utilizável end-to-end.

## Acceptance Criteria

1. Migration `supabase/migrations/0002_profiles.sql` (sucede placeholder `0001_init.sql` da Story 1.2) cria extensões `citext` e `pgcrypto` (ambas idempotentes, `IF NOT EXISTS`; `pgcrypto` necessária para seed.sql usar `crypt`/`gen_salt`), utility function `set_updated_at()` (trigger function genérica) e tabela `profiles` com colunas: `id uuid PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE`, `username citext NOT NULL UNIQUE`, `display_name text` (nullable, ≤ 50 chars), `bio text` (nullable, ≤ 280 chars), `avatar_url text` (nullable, regex `^https?://`), `created_at timestamptz NOT NULL DEFAULT now()`, `updated_at timestamptz NOT NULL DEFAULT now()`. **Sem coluna `theme`** em `profiles` (PRD AC1 textual lista `theme enum`, mas `docs/architecture/schema-design.md §4 #profiles` e `architecture.md §Database Schema` colocam `theme` em `pages` — `theme` será adicionado em Story 2.2; ver Project Structure Notes).
2. Constraint de `username`: `CHECK (username ~ '^[a-z0-9-]{3,30}$')` (3-30 chars, lowercase + dígitos + hyphen). Trigger `trg_profiles_set_updated_at BEFORE UPDATE` chama `set_updated_at()`. `COMMENT ON TABLE profiles` documenta propósito (1:1 com auth.users, FR4/FR13).
3. RLS policies em `profiles` (após `ALTER TABLE profiles ENABLE ROW LEVEL SECURITY`): (a) `profiles_select_public FOR SELECT USING (true)` — todo handle é público por design (arch §RLS High-Level Strategy linha 939); (b) `profiles_update_own FOR UPDATE USING (auth.uid() = id)` — owner-only update; (c) **nenhuma INSERT policy explícita** — INSERT acontece exclusivamente via trigger SECURITY DEFINER (AC4), não há permissão direta para `authenticated` ou `anon`; (d) **nenhuma DELETE policy** — delete cascade via `auth.users` ON DELETE CASCADE. Decisão arquitetural: a redação original do PRD AC3 ("`select_public` linha visível somente se referenciada por uma página publicada — refinado em Epic 2") é mais permissiva no MVP, conforme arch — ver Project Structure Notes.
4. Trigger function `on_auth_user_created()` (`LANGUAGE plpgsql SECURITY DEFINER SET search_path = public, pg_catalog`) lê `lower(NEW.raw_user_meta_data->>'username')`, valida não-vazio + length ≥ 3 (com `RAISE EXCEPTION` se inválido) e faz `INSERT INTO profiles (id, username) VALUES (NEW.id, v_username)`. Trigger `auth_user_created AFTER INSERT ON auth.users FOR EACH ROW` chama a função. **Escopo restrito ao MVP de Story 1.4:** trigger insere **apenas em `profiles`** (PRD/arch trigger canônico em `schema-design.md §4.Auth Trigger` também insere em `pages` — esse INSERT em `pages` é adicionado em Story 2.2 quando a tabela `pages` for criada; ver Project Structure Notes).
5. **CI job `test-integration` reativado** em `.github/workflows/ci.yml` (descomenta o bloco de Story 1.3 — CI-001 resolvido) provisionando um Supabase Branch por PR, rodando `supabase db push` e executando `pnpm test:integration` que cobre, no mínimo, os seguintes cenários RLS em `tests/integration/rls/profiles.test.ts`: (a) **owner read** — usuário autenticado lê seu próprio profile com sucesso; (b) **owner update** — usuário autenticado atualiza `display_name`/`bio`/`avatar_url` próprios e `updated_at` muda; (c) **non-owner read** — Bob lê profile de Alice via `select_public` (true) e recebe linha (comportamento esperado da policy permissiva); (d) **non-owner update bloqueado** — Bob tenta UPDATE profile de Alice e Supabase retorna erro com code `42501` ou mensagem contendo `RLS`; (e) **anonymous read** — cliente anon lê profiles publicamente (consistente com `select_public USING (true)`); (f) **anonymous update bloqueado** — cliente anon tenta UPDATE e falha com `42501`; (g) **direct INSERT bloqueado** — Alice (autenticada) tenta `INSERT INTO profiles` diretamente e falha (sem policy permissiva para INSERT por path não-trigger); (h) **trigger bootstrap** — após `supabase.auth.admin.createUser({ email, password, user_metadata: { username } })`, existe exatamente 1 linha em `profiles` com `id = user.id` e `username` correto (case-insensitive via `citext`).
6. Seed script `supabase/seed.sql` cria 3 profiles demo via `supabase.auth.admin.createUser` (ou equivalente SQL `auth.users` direto + chamada idempotente ao trigger) — usernames demo: `alice`, `bob`, `carol`; cada um com `display_name` e `bio` populados. Seed é **idempotente** (`ON CONFLICT DO NOTHING` ou guard `IF NOT EXISTS`) e **não é aplicado em produção** (comentário no topo do arquivo + documentação em `docs/dev-setup.md`). Conferir que `seed.sql` carrega sem erro contra um Supabase Branch limpo após `db push`.
7. Tipos TypeScript atualizados: `pnpm db:types` rodado contra projeto linkado regenera `lib/supabase/types.ts` agora com tipo concreto de `profiles` (não mais schema `public` vazio). `pnpm typecheck` continua exit 0. Commitar `lib/supabase/types.ts` atualizado.

### Profile — modelo conceitual e DDL canônico

[Source: docs/architecture.md §Data Models > Profile, linhas 201-228]

```typescript
export type Profile = {
  id: string;
  username: string;
  display_name: string | null;
  bio: string | null;
  avatar_url: string | null;
  created_at: string;
  updated_at: string;
};
```

**Relationships:** 1:1 → `auth.users` (FK em `id`, ON DELETE CASCADE); 1:1 → `Page` (preparado para 1:N em Phase 2 conforme PRD Story 2.2 — **não implementar `pages` nesta story**).

[Source: docs/architecture/schema-design.md §4 #profiles linhas 405-446]

DDL canônico (copiar literal na migration, com ajustes mínimos):

```sql
CREATE TABLE profiles (
  id           uuid PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
  username     citext NOT NULL UNIQUE
                 CHECK (username ~ '^[a-z0-9-]{3,30}$'),
  display_name text CHECK (display_name IS NULL OR length(display_name) <= 50),
  bio          text CHECK (bio IS NULL OR length(bio) <= 280),
  avatar_url   text CHECK (avatar_url IS NULL OR avatar_url ~* '^https?://'),
  created_at   timestamptz NOT NULL DEFAULT now(),
  updated_at   timestamptz NOT NULL DEFAULT now()
);

CREATE TRIGGER trg_profiles_set_updated_at
  BEFORE UPDATE ON profiles
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();

COMMENT ON TABLE profiles IS 'Identidade pública 1:1 com auth.users (FR4, FR13).';
COMMENT ON COLUMN profiles.username IS 'Handle público em /@username, lowercase + dígitos + hyphen (FR4).';
```

**Notes:**

- UNIQUE em `username` cria índice automático (não criar `idx_profiles_username` adicional — arch §schema-design.md linha 443 explícito: "Sem índices secundários adicionais").
- Reserved usernames (admin, api, dashboard, etc.) **NÃO** são CHECK constraint — validados em camada Server Action (`updateUsername`) com lista hardcoded em `lib/validators/reserved-usernames.ts`. Lista é responsabilidade de @dev em Story 1.5+ (UI de signup); aqui no schema apenas a regex `^[a-z0-9-]{3,30}$` é enforced.
- `avatar_url` regex `^https?://` é defensiva — validação semântica mais rica (domínio Supabase Storage) acontece em Server Action de upload.

### RLS Policies — Profiles

[Source: docs/architecture/schema-design.md §8 RLS High-Level Strategy linhas 935-944 + docs/architecture.md §Database Schema linhas 955-957]

**Decisão arquitetural canônica (arch §schema-design.md):**

| Operation | Policy                                        | Rationale                                                                                                                                                                            |
| --------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| SELECT    | `profiles_select_public USING (true)`         | Username é público por design — todo handle deve ser legível para suportar `/@username` SSR sem JOIN com pages. Performance: evita EXISTS subquery em todo render de página pública. |
| UPDATE    | `profiles_update_own USING (auth.uid() = id)` | Owner-only update; arch §schema-design.md linha 939.                                                                                                                                 |
| INSERT    | (nenhuma policy permissiva)                   | INSERT acontece exclusivamente via trigger SECURITY DEFINER (`on_auth_user_created`) que bypassa RLS. Sem policy = INSERT bloqueado para `anon`/`authenticated`.                     |
| DELETE    | (nenhuma policy permissiva)                   | DELETE acontece via CASCADE quando `auth.users` é deletado (Server Action `deleteAccount()` per arch §Authorization Model linha 980). Sem policy direta.                             |

[Source: docs/architecture.md §Database Schema linhas 948-957]

```sql
ALTER TABLE profiles ENABLE ROW LEVEL SECURITY;
CREATE POLICY "profiles_select_public" ON profiles FOR SELECT USING (true);
CREATE POLICY "profiles_update_own"   ON profiles FOR UPDATE USING (auth.uid() = id);
```

> **Hardening adicional:** considerar `WITH CHECK (auth.uid() = id)` no UPDATE policy para defesa em profundidade (impede update que troque `id` para outro user). É redundante porque `id` é PK + FK ON DELETE CASCADE, mas baixo custo.

### Trigger `on_auth_user_created` — Bootstrap automático

[Source: docs/architecture/schema-design.md §4 Auth Trigger linhas 644-678]

**Função canônica (hardening de Aria aplicado):**

```sql
CREATE OR REPLACE FUNCTION on_auth_user_created()
RETURNS trigger
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public, pg_catalog
AS $$
DECLARE
  v_username citext := lower(coalesce(NEW.raw_user_meta_data->>'username', ''));
BEGIN
  IF v_username = '' OR length(v_username) < 3 THEN
    RAISE EXCEPTION 'username missing or too short in raw_user_meta_data: %', v_username;
  END IF;

  INSERT INTO profiles (id, username) VALUES (NEW.id, v_username);

  RETURN NEW;
END;
$$;

CREATE TRIGGER auth_user_created
  AFTER INSERT ON auth.users
  FOR EACH ROW EXECUTE FUNCTION on_auth_user_created();

COMMENT ON FUNCTION on_auth_user_created() IS
  'Bootstrap profile ao criar auth.users. SECURITY DEFINER permite INSERT bypass RLS. Story 2.2 estende com INSERT em pages.';
```

**DIFERENÇA INTENCIONAL vs arch §schema-design.md linhas 660-666:** a versão canônica de arch ALSO faz `INSERT INTO pages (profile_id) VALUES (v_profile_id)`. Esta Story 1.4 **omite essa linha** porque a tabela `pages` ainda não existe (criada em Story 2.2). Story 2.2 fará:

```sql
CREATE OR REPLACE FUNCTION on_auth_user_created() ... -- substitui versão de 1.4
-- adicionando: INSERT INTO pages (profile_id) VALUES (NEW.id);
```

Esse "extend-pattern" está documentado em arch §10 Backward Compatibility como aceitável (`CREATE OR REPLACE FUNCTION` é zero-downtime). Cross-ref: Project Structure Notes #3 abaixo.

**Por que SECURITY DEFINER + `SET search_path`:**

- `SECURITY DEFINER` permite INSERT em `profiles` mesmo com RLS habilitado, porque executa com permissões do owner da função (postgres). Sem isso, o `anon` que dispara signup não conseguiria inserir.
- `SET search_path = public, pg_catalog` é hardening defensivo contra search_path injection em funções SECURITY DEFINER (recomendação Postgres + Supabase security advisory).
- Guard de username vazio/curto previne corrupção de dados se `raw_user_meta_data` vier malformado — UI de signup (Story 1.5) já valida client-side, mas defesa em profundidade.

### Technical Constraints

- **Postgres 15+:** `citext`, `SECURITY DEFINER`, `SET search_path` em function-level — todos suportados nativamente.
- **RLS performance:** policy `select_public USING (true)` é zero-overhead (compilada como always-true). Policy `update_own USING (auth.uid() = id)` faz lookup de função STABLE — postgres pode cachear. Sem riscos performáticos no MVP.
- **`citext` extension:** já criada em projetos Supabase managed por default em muitos casos; usar `IF NOT EXISTS` é idempotente.
- **Trigger ordering:** `trg_profiles_set_updated_at` (BEFORE UPDATE) executa antes de qualquer policy CHECK, mantendo `updated_at` sempre fresh mesmo em UPDATEs RLS-validated.
- **DEFERRABLE constraints:** não aplicáveis em `profiles` (Story 2.3 introduz DEFERRABLE em `links.position`).
- **Coding standards (arch §Coding Standards linhas 2384-2404):** esta story é majoritariamente SQL — as regras TS (Server-First, Validação Zod, ActionResult, Type Sharing, Service-role isolado, Env via Zod, Strict TS, Revalidação, PII hashada, rel=noopener, etc.) **não se aplicam ao DDL** diretamente. Aplicam-se ao código TS dos integration tests (use `Database` type de `lib/supabase/types`, não duplicar shape).
